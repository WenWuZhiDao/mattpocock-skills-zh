## 它做什么

`tdd` 测试先行地构建一个特性或修复一个 bug，一次一个行为，通过红-绿循环把代码逼出来。

它**不会**事先把所有测试都写完。事先批量写测试（"水平切片"）产出的是*想象中*行为的测试——它们检查的是事物的形状，对真实的改动却麻木不仁。`tdd` 转而采取垂直切片：一个测试，然后刚好够让它通过的代码，再下一个测试，每个循环都受上一个循环所教给你的东西启发。测试只瞄准公共接口，所以底下的实现可以改变而测试不必挪动。

## 何时使用它

输入 `/tdd`，或者当任务契合时智能体会自动触发它——测试先行地构建一个特性或修复一个 bug，或者当你说"red-green-refactor"时。

当有一个具体的行为要构建、而你想要能在重构后存活的测试时，就用它。如果行为还没敲定，先把规格定下来——为此请用 [to-spec](https://aihero.dev/skills-to-spec)。当工作真正关乎的是接口的形状而非测试时，请用 [codebase-design](https://aihero.dev/skills-codebase-design)；`tdd` 在规划期间会调用它以取用深模块词汇。

## 红-绿，一次一片

领头的理念是**红-绿循环**：写一个失败的测试（红），加上刚好够让它通过的代码（绿），然后为下一个行为重复——每个循环都受上一个循环所教给你的东西启发。第一个循环是一颗**曳光弹**：一个证明单条路径端到端跑通的测试，然后你再从它向外构建。因为你刚写完那段代码，你确切地知道哪个行为要紧、以及如何验证它——你绝不会因为投入一个自己尚不理解的测试结构而跑到自己的车灯前头去。

两条规则让测试保持诚实。一个好的测试读起来像一份规格说明（"用户可以用有效的购物车结账"），并通过公共 API 走真实的代码路径，所以重命名一个内部函数绝不会弄坏它。而期望值来自一个独立的真相来源——一个已知良好的字面量、一个演算过的例子、规格——绝不用代码计算它们的方式去重新计算，那正是一个**同义反复**的测试如何靠构造而通过、却什么都不告诉你。

重构只在套件为绿之后才发生；绝不在红的时候进行。

## 它生效的标志

- 它写一个测试、让它通过，然后才写下一个——而不是一批测试后面跟一批代码。
- 测试命名的是行为，而非内部实现，并且能在内部重命名后存活。
- 期望值是来自规格的字面量，而不是用代码推导它们的同一方式推导出来的数字。

## 它的位置

`tdd` 是主构建链为了写代码而运行的红-绿循环：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

[implement](https://aihero.dev/skills-implement) 是链条的构建步骤，它在内部驱动 `tdd`，测试先行地构建每一张工单，然后再交接给 [code-review](https://aihero.dev/skills-code-review)——所以 `tdd` 是那个步骤内部的引擎，而不是它自己的一个步骤。你也可以直接取用它，每当有一个具体行为要构建而没有完整规格时。它的另一个邻居是 [codebase-design](https://aihero.dev/skills-codebase-design)，`tdd` 倚赖它去找到值得在其上测试的深模块接缝。当你不确定该用哪个技能或流程时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你指路。

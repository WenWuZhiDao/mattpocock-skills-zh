## 它做什么

`code-review` 沿两个维度评审 `HEAD` 与你指定的某个固定点之间的差异——某个提交、某个分支、某个标签、`main`、`HEAD~5`。**标准**维度问的是代码是否遵循了本仓库编写代码的方式。**规格**维度问的是代码是否做到了发起它的 issue 或[规格](https://www.aihero.dev/ai-coding-dictionary/spec)所要求的事。每个维度都在各自的[子代理](https://www.aihero.dev/ai-coding-dictionary/subagent)中运行，因此谁都看不到对方的推理。

这两个维度从不合并，也从不重新排名。报告在结尾给出*每个维度各自*的最严重问题，并拒绝在二者之间指定一个总冠军，因为一处改动可能通过一个维度而未过另一个：遵循了每一条约定却实现了错误的东西，就通过标准而未过规格；恰好做到了[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)所要求的却破坏了仓库约定，则反之。一个混合的裁决会让通过的维度替未过的那个维度打掩护。

## 何时使用它

输入 `/code-review`，或者当你要求评审某个分支、某个 PR、进行中的工作，或任何「自 X 以来」的内容时，代理会自动使用它。

| 你的情境 | 使用 |
| --- | --- |
| 差异已存在，你想知道它是否构建得当*并且*是不是要做的对的东西 | `code-review` |
| 你想在差异里搜捕 bug——空指针路径、竞态、差一错误 | Claude Code 自带的评审，而非这一个（见下文的名称冲突） |
| 什么都还没写，而你想以测试先行的方式来写 | [tdd](https://aihero.dev/skills-tdd) |
| 需要构建一整份规格，包含评审 | [implement](https://aihero.dev/skills-implement)，它自己会调用本技能 |
| 是整个代码库都漂移了，而非单个差异 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) |
| 有东西坏了，而你不知道原因 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

你必须提供那个固定点。如果你不提供，技能会向你索要而非猜测；随后它会检查该 ref 能否解析、差异是否非空，然后才派生任何东西，这样一个打错的分支名会在你眼前失败，而不是在两个子代理内部失败。

## 前置条件

标准维度什么都不需要。它读取仓库所记录的一切（`CODING_STANDARDS.md`、`CONTRIBUTING.md` 之类），当仓库什么都没记录时则退回到一个内置基线。

规格维度需要存在一份规格且可被找到。它按此顺序查找：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67`），经由 `docs/agents/issue-tracker.md` 获取。
2. 你作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能名匹配的规格文件。
4. 询问你。

第 1 步依赖 `docs/agents/issue-tracker.md`，它由 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 写入。没有它，只要你递给它一个路径，该维度仍能工作。若根本没有规格，规格子代理会被跳过，报告会写「无可用规格」而非凭空编造需求。

## 两个维度

| | 标准 | 规格 |
| --- | --- | --- |
| 问题 | 是否构建得当？ | 是不是要做的对的东西？ |
| 读取 | 仓库所记录的标准，外加坏味道基线 | 发起它的 issue 或规格 |
| 报告 | 有据可查的违规（可为硬性），以及坏味道（永远是判断题） | 缺失或部分实现的需求、范围蔓延、实现错误的需求 |
| 每条发现都引用 | 标准文件及其规则，或指名的坏味道加上代码块 | 规格中的那一行 |

一个不了解你标准的通用评审技能，正是这套设计力图避免的东西——它会标出你代码库中刻意为之的部分，又漏掉你代码库实际依赖的不变量。所以仓库自身的文档是标准维度上的[一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)，且**仓库始终优先**。

**坏味道基线**是其下的底线：出自《重构》第 3 章的十二种 Fowler 代码坏味道——神秘命名、重复代码、依恋情结、数据泥团、基本类型偏执、重复的 switch、霰弹式修改、发散式变化、夸夸其谈通用性、过长的消息链、中间人、被拒绝的遗赠。每一种都是带标签的启发式（「可能的依恋情结」），从不是硬性违规，且每一种都表述为*它是什么*→*如何修复*，因此一条发现附带一个动作而非一句抱怨。凡是你的 linter 已经强制执行的，两个维度都会跳过。

## 常见问题

**它和 Claude Code 自带的 `/code-review` 冲突了。我该怎么办？**

这是本技能被报告最多的问题，且尚未修复。Claude Code 自带一个 `/code-review`，它做的是另一件事——它在差异里搜捕 bug，而这一个检查的是规格符合度和仓库标准。安装本库意味着二者之一会胜出，而谁胜出取决于你如何安装。经由插件市场安装时，一切都会以 `mattpocock-skills:` 前缀取别名，自带的那个在非限定名下变得难以够到；经由普通的 skills 安装时，本地文件胜出，本技能会遮蔽自带的那个。一个干净的答案是彻底移除 Claude Code 的自带技能：这是一次可观的[上下文](https://www.aihero.dev/ai-coding-dictionary/context)节省，而且冲突从此不再要紧。这种遮蔽本身可以说是 Claude Code [载体](https://www.aihero.dev/ai-coding-dictionary/harness)的 bug——技能作者本应可以随意为技能命名——所以另一个答案是重命名本地副本。编辑 frontmatter 或重命名目录都会被 `npx skills update` 撤销；用户报告的经久之法是把技能 fork 成一个新名字，并把 `code-review` 从受管理的那套里剔除，同时记下你 fork 自哪个提交，以便日后手工重新同步。

**它的子代理不断重新调用 `/code-review` 并派生出更多代理。**

已知的开放 bug，被数人在不止一个载体中复现。标准与规格提示词并未禁止委派，所以一个子代理可以重新发现该技能并再度扇出——一份报告达到了 50 多个代理。人们在 fork 上采用的修复是往两份子代理简报末尾各追加一行：「不要调用 `/code-review` 或派生额外代理——直接执行本次评审。」有些人更愿意在载体层面处理，好让每个技能都继承这道防护。二者都还未进入已发布的技能。如果你无人值守地运行它，请盯着代理数量。

**我应该在编写这段代码的同一次[会话](https://www.aihero.dev/ai-coding-dictionary/session)里运行它吗？**

倾向于开一个新的。正如一位读者所说：「同一份上下文评审自身不是评审，而是带斜杠命令的确认偏误。」编写会话里做评审的代理持有塑造了代码的每一个假设，而那恰恰是独立评审者不会拥有的上下文。这也是为什么人们要求一个不带内置评审步骤的 [implement](https://aihero.dev/skills-implement)——它把评审跑在刚写完那份差异的同一次会话里。从一个干净的会话中亲自调用 `/code-review` 才是诚实的版本。

**每个工单之后，还是在最后一次性做？**

两者都行，技能不替你决定。逐工单能让每份差异小到足以让规格维度有一份清晰的规格可对照，这正是 `implement` 采用的模式。批到分支末尾则能抓住逐工单各次评审都漏掉的工单之间的交互。如果拿不准，就逐工单评审，并在最后针对分支起点跑一遍收尾。

**我能信任这些发现吗？**

不核实就不能。子代理的输出是假设而非证据——某个团队报告了十几处破坏性改动，而基于散文的评审都放行了。技能是把两份报告逐字或稍加清理地汇总，而非逐条对照文件重新核实，所以一条发现可能引用错误的位置或夸大某个影响。行动之前，先读每条发现上的引用。每条发现都被要求携带一个引用——一条标准规则、一种坏味道加上其代码块，或一行规格——正是这一点让此事根本可核。

**为什么我每次运行它都会发现新问题？**

因为修复会创造新的暴露面，也因为标准维度中判断题的那一半在多次运行之间并非确定性的。一位读者把这个循环讲得很直白：「`/code-review` 和 `/improve-code-architecture` 每次都能找出新东西。我实现修复、重跑这些技能，一次又一次。」不存在收敛保证。把一次评审当作一份线索清单，处理那些背后有引用规则的，然后停手——不要循环运行直到它干净地返回，因为它不会。

**它评审我未提交的工作吗？**

不。它比较的是 `<固定点>...HEAD`，三个点，即从合并基点起算，并排除已暂存和工作区的改动。如果 `implement` 没有做过一次中间提交，那么正要提交的工作对评审是不可见的。先提交，再评审，然后修订或追加一个 fixup。

## 它生效的标志

- 遇到坏的 ref 或空差异时，它会在派生任何子代理之前就拒绝开始。
- 报告以 `## Standards` 与 `## Spec` 下的两个独立区块到达，而非一份合并的清单。
- 每条标准发现都指名你仓库某个文件里的一条规则或十二种坏味道之一，并引用代码块；每条规格发现都引用规格中的一行。
- 收尾摘要给出每个维度各自的最严重问题，并拒绝挑选一个总冠军。
- 在无可用规格时，规格区块如实说明，而非罗列它从代码推断出的需求。

## 它的位置

`code-review` 是构建链尾部的评审步骤——`grill-with-docs → to-spec → to-tickets → implement → code-review`——同时也能独立作用于你指向它的任何分支或 PR。

- [implement](https://aihero.dev/skills-implement) 是最近的邻居：它驱动构建，并在提交前把本技能当作自己的收尾评审来调用。
- [to-spec](https://aihero.dev/skills-to-spec) 和 [to-tickets](https://aihero.dev/skills-to-tickets) 产出规格维度对照的那份文档；一份含糊的规格会让该维度也含糊。
- [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 是面向整个代码库的对应物——本技能永远只看一个差异。

当你不确定情境需要哪个技能时，[ask-matt](https://aihero.dev/skills-ask-matt) 会在整套技能之间为你路由。

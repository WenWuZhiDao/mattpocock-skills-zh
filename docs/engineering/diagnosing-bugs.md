## 它做什么

`diagnosing-bugs` 对一个棘手的 bug 或一次性能回退运行一套六阶段诊断：构建复现、最小化它、给假设排序、加装探针、连同回归测试一起修复、清理。

在存在一个**紧凑**的反馈循环之前，它不会让代理形成任何理论——那是一条被指名的命令，已经跑过一次，在*这个* bug 上变红、在它被修复时变绿。一个拿到 bug 报告的编码代理的默认行为是读代码、猜；这个技能阻止那样做。如果不存在能变红的命令，就没有第 2 阶段。那道唯一的关卡正是这个技能的意义所在。它之后的一切——二分、假设检验、加装探针——一旦信号存在便都是机械的。

## 何时使用它

输入 `/diagnosing-bugs`，或者当某个任务契合时代理会自行使用它——它是模型调用型，在「诊断」/「调试这个」或在关于某处坏了、抛错、失败或变慢的报告上触发。

在棘手的问题上使用它：一个第一眼看不透的 bug、一次间歇性的抖动、一次在两个已知良好状态之间悄悄溜进来的回退。它按设计就是重型的，对于你想用一条消息就得到答案的问题是错误的工具。

| 你的情境 | 去哪里 |
| --- | --- |
| 一个你能描述成症状的具体缺陷 | 本技能 |
| 一个慢的端点或有已知前后对照的时序回退 | 本技能——它有一条性能分支（先测一个基线，再二分） |
| 「这个代码库的瓶颈在哪里？」——没有具体症状 | 不是本技能。它诊断一个已知的失败，不做审计 |
| 别人给的原始 bug 报告，尚未确认或写清 | 先 [triage](https://aihero.dev/skills-triage) |
| 用来回答设计问题的一次性代码，而非追缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 以测试先行的方式构建一项计划中的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 不存在能把 bug 锁定的好接缝 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)——本技能自己会在那里交接 |

## 紧凑的循环就是这个技能

第 1 阶段获得不成比例的投入，因为它是唯一困难的阶段。技能给出一架构造循环之法的阶梯，大致按偏好排序：

1. 在任何能够到 bug 的接缝处的一个失败测试。
2. 针对正在运行的开发服务器的一个 curl 或 HTTP 脚本。
3. 带 fixture 输入的一次 CLI 调用，与一个已知良好的快照做差异比较。
4. 一个对 DOM、控制台或网络做断言的无头浏览器脚本。
5. 一次重放的捕获——一个保存的请求、载荷或事件日志，孤立地跑过该代码路径。
6. 一个一次性载体：系统的一个最小子集，一次函数调用。
7. 一个属性或模糊循环，用于「有时输出错误」。
8. 一个你能交给 `git bisect run` 的二分载体。
9. 一个差分循环——同样的输入，旧版本对新版本。
10. 一个[人在环中](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)的 bash 脚本，最后手段。技能为此附带了 `scripts/hitl-loop.template.sh`：代理运行该脚本，你在终端里跟着提示走，你的回答作为可解析的输出返回。

*一个*循环不是目标。**紧凑**才是：快（数秒）、确定（每次运行同样的裁决）、锐利（断言你确切的症状，而非「没崩」）、且能被代理无人值守地运行。一个 30 秒的抖动循环几乎不比没有强。对于只是偶尔出现的 bug，目标不是一个干净的复现，而是一个**更高的复现率**——循环触发条件、并行化、加压、注入 sleep，直到抖动率高到足以据以调试。

当它确实无法构建一个时，它被指示停下并如实说明、列出它试过什么，并向你索要[环境](https://www.aihero.dev/ai-coding-dictionary/environment)访问权、一个捕获的产物，或添加临时探针的许可。它不应无论如何径直去做假设。

## 阶段之间的关卡

这些阶段是关卡，而非清单。每一道都拒绝打开，直到某件具体的事为真。

| 关卡 | 什么必须为真 |
| --- | --- |
| 进入第 2 阶段 | 一条被指名的命令，已经跑过并连同其输出粘贴出来，能在这个 bug 上变红 |
| 进入第 3 阶段 | 复现被复现出来*且*被最小化——每一个剩下的元素都是承重的 |
| 进入第 4 阶段 | 存在 3–5 个已排序、可证伪的假设，每个都陈述其预测，并在任何一个被检验之前展示给你 |
| 进入第 5 阶段 | 探针对应到某个具体预测，一次一个变量，每条 debug 日志都以 `[DEBUG-a4f2]` 的形式打标签，好让清理只需一次 grep |
| 完成 | 原始复现不再复现、探针已移除，且事实证明正确的那个假设被写进提交信息 |

第 5 阶段有一个值得知道的逃生舱口。回归测试在修复之前编写，但仅当存在一个**正确的接缝**——一个测试能在调用点按真实 bug 模式发生的样子去施展它的接缝。当唯一可用的接缝太浅时，技能被告知如实说明，而非写一个会给出虚假信心的测试。那种缺失本身就是发现，也正是它把复盘路由到 `improve-codebase-architecture` 的原因。

## 常见问题

**它在我只想要一个直接答案的快速问题上触发了。**
这是这个技能被报告最多的问题，而且是真实的。尤其在 GPT-5.6-Sol 上，用户报告它在对一个问题的平实描述上触发：「模型转而触发了相当正式的 diagnosing-bugs 技能。它接着去构造一个复现场景——常常搭一个价值有限的 mock 场景——然后才给我一个回复或建议。这导致了相当大的回复延迟。」四个各自独立的人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上报告了同样的形态。被接受的修复是从一个更轻的方式起步，仅在问题确有需要时才升级到更重的那个，但那项改动尚未落地。这个技能是对着 Claude Code 的调用行为校准的；一个激活阈值更低的[模型](https://www.aihero.dev/ai-coding-dictionary/model)会过度触发它。在它做成分级之前，实用的修复是说出你想要什么（「就回答这个，别诊断」），或者在你的[载体](https://www.aihero.dev/ai-coding-dictionary/harness)里为它关闭模型调用。

**我能把它指向一个代码库、问性能问题在哪吗？**
不能。它诊断一个你已经能指名的失败。它的性能分支是针对有症状的回退——建立一个基线测量，然后二分，先测量后修复——而不是针对主动的扫查。一个针对主动版本的技能[已被提议并关闭](https://github.com/mattpocock/skills/issues/431)；目前没有针对它的技能。

**它在写修复之前会停下来问我吗？**
不会。只有第 3 阶段有一个人类检查点——已排序的假设清单在任何一个被检验之前展示给你，而如果你不在，它会按自己的排序继续。加装探针和修复之间没有关卡，所以代理可以在你还没认同它的根因之前就开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求那道关卡，仍然开放。如果你想要它，就在调用技能时说出来。

**我已经对这份 bug 报告跑过 `/triage` 了。这是同一份工作再来一遍吗？**
部分是，而两个技能都不承认这一点。正如一位读者所说：「Triage 的第 3 步本质上是 diagnosing-bugs 第 1–2 阶段的一个浅而有界的实例，但两个文件谁都没提到对方。」Triage 做一次有界的「这到底是不是 bug、暴露面是什么」的检查；本技能做彻底的版本。先跑 triage 不算白费——它的验证常常给你第 1 阶段的大部分原材料——但要预料到得在这里正经重做一遍，也要预料到不会有交叉引用来告诉你这一点。

**它粘贴的复现输出会泄漏机密吗？**
可能会。技能要求代理粘贴调用及其输出，并索要像 HAR 文件、日志转储和 core dump 这样的产物。这些没有一个是被指令清洗过的。[Issue #674](https://github.com/mattpocock/skills/issues/674) 提出的正是这一点——凭据、token、cookie 和个人数据搭便车进入一次聊天、一个 issue 或一个 PR——并提议一道脱敏护栏。它开放且未实现。眼下把脱敏当作你自己的活，尤其在输出流向任何公开之处之前。

**我的安全扫描器把这个技能标为高风险。**
Snyk 会标它，而这个标记是误报。它是这套技能里唯一附带一个可执行 shell 脚本（`hitl-loop.template.sh`）、连同运行它以及 curl 一个开发服务器的指令的技能。附带的 `.sh` 加上运行它的指令加上出站 HTTP，就足以绊倒一个静态扫描器。脚本本身约 30 行 `read -r -p` 提示，为人类输入而暂停。扫描器评的是能力面，而非一个被证实的漏洞利用。

**`/diagnose` 怎么了？**
在 v1.0.0 里重命名为 `/diagnosing-bugs`。旧名字不再存在。你那边任何串接 `/diagnose` 的东西——一个包装技能、一个保存的提示词——都需要更新。

## 它生效的标志

- 在给出任何一个理论之前，它先给你看一条命令及其变红的输出。如果理论先到，那这个技能就没在运行。
- 它复现出的失败正是你报告的那个，而不是它半路上发现的一个邻近的。
- 它在开始猜测之前收缩复现，并能告诉你每个剩下的部件为何是承重的。
- 在任何一个假设被检验之前，你会看到一份 3–5 个假设的排序清单，每个都带有一个你能证伪的预测。
- 它添加的每条 debug 日志都带一个像 `[DEBUG-a4f2]` 的标签，而当它宣布完成时对那个标签的 grep 返回为空。
- 提交或 PR 信息指明哪个假设是对的。
- 当它无法用一个测试把 bug 锁定时，它如实说明，而非写一个浅的。

## 它的位置

`diagnosing-bugs` 是一个随时可用的独立技能。当有东西坏了时你跳进它，当修复及其回归测试到位时你跳出来；它不持有状态，也不需要任何前置设置。[ask-matt](https://aihero.dev/skills-ask-matt) 把「有东西坏了」路由到这里。

有两个邻居要紧。当真正的发现是代码没有接缝能把 bug 锁定时，[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 接过[交接](https://www.aihero.dev/ai-coding-dictionary/handoff)——这个建议是在修复到位之后、信息更多时才作出的。[triage](https://aihero.dev/skills-triage) 位于它的上游，用于以他人原始报告形式到来的 bug，做的是同样的头两个阶段的一个更浅的版本。

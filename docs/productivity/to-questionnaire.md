## 它做什么

`to-questionnaire` 把一个你无法独自敲定的决定，变成一份**问卷**——一个 Markdown 文档，你把它交给那个掌握着你所缺信息的人，让对方异步填写，或者你们两人在一次会议上一起过一遍。

它拷问的是**发送这件事**，而绝非主题。在这里就主题访谈你毫无意义：不懂这个主题正是你要写给别人的原因。所以它只问那两件你永远能回答的事——这要发给谁，以及你需要从对方那里得到什么——并把文档里的每一个问题都瞄准这两者之间的**缺口**。

## 何时使用它

你通过输入 `/to-questionnaire` 来调用它——[智能体（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)不会自行使用它。

当一个决定卡在只存在于另一个人脑袋里的知识上时使用它：一位客户、一位领域专家、一位掌握业务规则的高管、一位不与你同组的同事。你需要哪个技能，取决于答案究竟在哪里：

| 答案在…… | 使用 |
| --- | --- |
| 你自己的脑袋里，尚未磨砺 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的脑袋里 | `to-questionnaire` |
| 还不在任何人脑袋里——这个问题需要有东西可供反应 | [prototype](https://aihero.dev/skills-prototype) |

常见情形是一场[拷问（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling)会话停滞了：浮现出的一些东西不是你能回答的。就在那同一场对话里运行 `/to-questionnaire`，把那些问题转到线下，然后把答案带回来继续。

## 是发送，不是主题

访谈是两轮交流，然后就停。

- **这要发给谁？** 对方的角色、专长、与你的关系。这确定了语气，以及文档必须携带多少上下文——一位外部客户需要被引导进入状况，一位队友则不需要。
- **你需要得到什么？** 那些你无法独自解决的具体决定或事实。这成为衡量成品文档的清单：你点名的每一项都会得到一个瞄准它的问题。

此后的一切都是起草。文件落在当前目录下的 `to-questionnaire-<slug>.md`。没有设置，没有工作区，也没有任何要配置的东西。

## 这份文档

它被框定为一份**发现式问卷（discovery questionnaire）**——你缺少上下文，收件人掌握它——而这个框定驱动了它的形态：

- 一行目的语，点名骑在它上面的那个决定，以及一个简短的上下文小节，给一个从未在你脑袋里的收件人。
- 问题按**最重要者优先**排序，并归入带主题的标题下，因为异步意味着你可能只有一次机会。
- 每个问题只装一个想法，绝不复合，下面附一个答案存根，只有当一个问题可能被误读时才加一行*这为什么重要*。
- 明确允许回答「我不知道」——一个被标记的不确定是有用的；一个读起来像事实的自信猜测则不是。
- 一个收尾的兜底问题：有什么我们没问、但我们本该知道的吗？

有两件事它刻意不是。它不是**分支式的**——问题是一个扁平的、分组的列表，而非一棵会在你回答了 A 就跳过 D 节的树。它也不是**多收件人的**——一次运行为一个人产出一份文档。

## 常见问题

**它会读我的拷问会话并从中抽取问题吗？**
不作为它自己的一个步骤。这个技能没有摄取阶段：它先问发送这件事，然后起草。让它在一场拷问会话之后奏效的，是你在**同一场对话**里运行它，于是那个[会话（session）](https://www.aihero.dev/ai-coding-dictionary/session)已经在[上下文（context）](https://www.aihero.dev/ai-coding-dictionary/context)里，起草便能借用它。在一个全新会话里启动它，它对那场拷问一无所知——当你回答「你需要得到什么？」时，你将自己重新供给主题。

**缺失的答案并非全在同一个人那里。它能按收件人拆分吗？**
不能。第一步问*那位*收件人，单数，而整份文档的语气和上下文都是冲着对方定的。如果三个人掌握答案的三个部分，就运行三次，一人一次。在单一文档内按学科或角色路由问题，是有人提过的请求；它不是已发布的东西。

**问题是相依的吗——它会根据先前的回答跳过某些节吗？**
不会。相依问题的设计被探索过，但没有发布。输出是一份静态文档：带主题的分组、最重要者优先、每个问题都在生效。反对它的理由是公允的——一个[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)在一个真实答案之前提前规划超过两三个问题，规划得就很糟，而一份分支式文档必须在每个答案之前提前规划好全部问题。

**如果收件人也不知道怎么办？**
文档会告诉对方就这么说。「我不知道」和部分答案都被明确要求，而一个被标记的不确定比一个猜测更有价值，因为一个含糊的答案和一个自信错误的答案，一旦回到你的上下文里就长得一模一样。

**它会把它发到什么地方吗——Slack、issue 跟踪器、邮件？**
不会。它在当前目录写一个 Markdown 文件并告诉你路径。递送归你：粘进一张[工单（ticket）](https://www.aihero.dev/ai-coding-dictionary/ticket)、丢进一个 Slack 线程、附到一封邮件里，或者在一块共享屏幕上打开它、当场过一遍。这四种人们都手动接过。

**这不就是批量模式的 `/grill-me` 吗？**
不是，而且这个区别值得记住。`grill-me` 已经以**轮次**提问——一次问整个前沿，然后从你的回答重新计算——所以「一次把所有问题都给我」的需求在那里已被满足。`to-questionnaire` 讲的是另一个维度：不是问题如何被递送，而是答案在谁的脑袋里。让你自己更快地回答它们是 `grill-me`；把它们从别人那里弄出来是这个。

**没有技能我不也能直接让智能体做这个吗？**
能，而且在它存在之前很多人就这么做了——`OPEN_QUESTIONS.md` 文件、发给客户的电子表格、每个未答问题一张「需要更多信息」的工单。这个技能给你买到两样东西：访谈绝不会飘到主题上，而文档出来时是一个非技术收件人真能填的形态。如果你已经有一套管用的自家格式，诚实的回答是你不需要这个。

## 它生效的标志

- 它问收件人、问你需要得到什么，然后就停止提问。一个关于主题本身的问题，就是这个技能跑偏了。
- 你点名为「我需要得到什么」的每一项，都能追溯到文件里的一个问题。
- 那些问题读起来是瞄准*收件人*所知的，而不是把你自己的未决问题逐字抄下来。
- 你能把文件交给一个不在对话里的人，而对方会知道为什么收到它、以及该在何时回复。
- 回来的答案是新一轮拷问的可用输入，而不是一套全新的问题。

## 它的位置

`to-questionnaire` 是一个随时可取用的独立技能。它坐落在你自身知识的边界上，那里下一步是另一个人而非另一个技能——最常见于流程中途，当规划卡在某件不是你能决定的事上时。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，二者在答案所在之处上分道：拷问开采你，问卷开采别人。回来的东西是原材料——把它喂进新一轮拷问，或者如果工作正走向构建，就喂进 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。当你不确定此刻哪个技能合适时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你导航。

# 接口设计

当用户想为某个选定的深化候选项探索备选接口时，使用这套并行子代理模式。本方法基于「Design It Twice」（Ousterhout）——你的第一个点子不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**module（模块）**、**interface（接口）**、**seam（缝）**、**adapter（适配器）**、**leverage（杠杆）**。

## 流程

### 1. 框定问题空间

在派生子代理之前，为选定的候选项写一段面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖的依赖，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意性代码草图，用来锚定约束——不是提案，只是把约束具体化的一种方式

把这段展示给用户，然后立即进行第 2 步。用户在阅读和思考的同时，子代理在并行工作。

### 2. 派生子代理

用 Agent 工具并行派生 3 个以上子代理。每个都必须为深化模块产出一个**截然不同**的接口。

用一份独立的技术简报（文件路径、耦合细节、[DEEPENING.md](DEEPENING.md) 中的依赖类别、缝背后是什么）来提示每个子代理。该简报独立于第 1 步中面向用户的问题空间说明。给每个代理一个不同的设计约束：

- 代理 1：「最小化接口——目标最多 1–3 个入口点。每个入口点的杠杆最大化。」
- 代理 2：「最大化灵活性——支持许多用例和扩展。」
- 代理 3：「为最常见的调用方优化——让默认情形变得微不足道。」
- 代理 4（如适用）：「围绕端口与适配器为跨缝依赖做设计。」

在简报中同时包含 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，这样每个子代理都能与架构语言和项目领域语言一致地命名。

每个子代理输出：

1. 接口（类型、方法、参数——外加不变量、顺序、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现在缝背后隐藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——哪里杠杆高，哪里单薄

### 3. 呈现与比较

按顺序呈现各设计，让用户能逐一吸收，然后用散文形式比较它们。从**深度**（接口处的杠杆）、**局部性**（变更在哪里集中）、**缝的放置**三方面对比。

比较之后，给出你自己的推荐：你认为哪个设计最强，以及为什么。如果不同设计中的元素能良好结合，就提议一个混合方案。要有主见——用户想要一个有力的判断，而不是一份菜单。

# 语言（Language）

本技能给出的每条建议所共享的词汇。精确使用这些术语——不要替换成「组件（component）」「服务（service）」「API」或「边界（boundary）」。语言保持一致正是全部要点所在。

## 术语

**Module（模块）**
任何有接口和实现的东西。刻意做到与规模无关——同等适用于函数、类、包，或跨层切片。
_避免_：unit（单元）、component（组件）、service（服务）。

**Interface（接口）**
调用方为正确使用模块所必须知道的一切。包括类型签名，但也包括不变量、顺序约束、错误模式、所需配置和性能特征。
_避免_：API、signature（签名）（太狭隘——它们只指类型层面的表面）。

**Implementation（实现）**
模块内部的东西——它的代码本体。与 **Adapter** 不同：一个东西可以是小适配器配大实现（一个 Postgres 仓库），也可以是大适配器配小实现（一个内存假实现）。当缝是话题时用「适配器」；否则用「实现」。

**Depth（深度）**
接口处的杠杆——调用方（或测试）每学习一单位接口能驱动多少行为。当大量行为坐落在一个小接口背后时，模块是**深的**。当接口几乎和实现一样复杂时，模块是**浅的**。

**Seam（缝）** _（来自 Michael Feathers）_
一个你可以不在该处就地编辑就改变行为的地方。模块接口所在的*位置*。选择把缝放在哪里本身就是一项设计决策，与缝背后放什么相区别。
_避免_：boundary（边界）（与 DDD 的限界上下文重载冲突）。

**Adapter（适配器）**
在某个缝处满足某接口的具体东西。描述的是*角色*（它填的是哪个槽），而非实质（里面是什么）。

**Leverage（杠杆）**
调用方从深度中得到的东西。每学习一单位接口就获得更多能力。一份实现在 N 个调用点和 M 个测试上得到回报。

**Locality（局部性）**
维护者从深度中得到的东西。变更、缺陷、知识和验证集中在一处，而不是散布到各调用方。改一次，处处皆改。

## 原则

- **深度是接口的属性，而非实现的属性。**一个深模块内部可以由小的、可 mock 的、可替换的部件组成——它们只是不属于接口的一部分。一个模块可以有**内部缝**（私有于其实现，供它自己的测试使用），也可以在其接口处有**外部缝**。
- **删除测试。**设想删掉这个模块。如果复杂度消失了，那模块就没藏什么（它是个传递层）。如果复杂度在 N 个调用方处重新出现，那模块就是物有所值的。
- **接口就是测试面。**调用方和测试跨越的是同一道缝。如果你想测试接口*之外*的东西，那模块大概形状不对。
- **一个适配器意味着假设的缝。两个适配器意味着真实的缝。**除非确实有东西跨缝变化，否则不要引入缝。

## 关系

- 一个 **Module** 恰好有一个 **Interface**（它向调用方和测试呈现的表面）。
- **Depth** 是某个 **Module** 的属性，相对其 **Interface** 来衡量。
- **Seam** 是某个 **Module** 的 **Interface** 所在之处。
- **Adapter** 坐落在某个 **Seam** 处并满足该 **Interface**。
- **Depth** 为调用方产生 **Leverage**，为维护者产生 **Locality**。

## 被否决的提法

- **把深度当作实现行数与接口行数之比**（Ousterhout）：会奖励往实现里灌水。我们改用「深度即杠杆」。
- **把「接口」当作 TypeScript 的 `interface` 关键字或一个类的公共方法**：太狭隘——这里的接口包括调用方必须知道的每一项事实。
- **「边界」**：与 DDD 的限界上下文重载冲突。请说 **seam（缝）** 或 **interface（接口）**。

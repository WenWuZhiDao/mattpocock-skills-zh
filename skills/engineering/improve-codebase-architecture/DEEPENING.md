# 深化（Deepening）

如何在给定依赖的情况下，安全地深化一簇浅模块。本文假定你已熟悉 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**module（模块）**、**interface（接口）**、**seam（缝）**、**adapter（适配器）**。

## 依赖分类

在评估一个深化候选项时，给它的依赖分类。类别决定了深化模块如何跨其缝来测试。

### 1. 进程内（In-process）

纯计算、内存内状态、无 I/O。永远可深化——把模块合并，直接通过新接口测试。不需要适配器。

### 2. 本地可替代（Local-substitutable）

有本地测试替身的依赖（用 PGLite 替 Postgres，用内存文件系统替文件系统）。如果替身存在则可深化。深化模块在测试套件里跑着替身来测试。缝是内部的；模块的对外接口上没有端口。

### 3. 远程但自有（端口与适配器，Ports & Adapters）

你自己的、跨网络边界的服务（微服务、内部 API）。在缝处定义一个**端口（port）**（接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

推荐措辞形态：*「在缝处定义一个端口，为生产实现一个 HTTP 适配器、为测试实现一个内存适配器，这样即使部署上是跨网络的，逻辑也坐落在一个深模块里。」*

### 4. 真正的外部（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化模块把外部依赖作为注入的端口；测试提供一个 mock 适配器。

## 缝的纪律

- **一个适配器意味着假设的缝。两个适配器意味着真实的缝。**除非至少能证明需要两个适配器（通常是生产 + 测试），否则不要引入端口。单适配器的缝只是间接层。
- **内部缝 vs 外部缝。**一个深模块可以有内部缝（私有于其实现，供它自己的测试使用），也可以在其接口处有外部缝。不要仅仅因为测试用到了内部缝，就把它们通过接口暴露出去。

## 测试策略：替换，而非叠加

- 一旦在深化模块的接口处有了测试，浅模块上的旧单元测试就成了废料——删掉它们。
- 在深化模块的接口处写新测试。**接口就是测试面。**
- 测试断言通过接口可观察到的结果，而不是内部状态。
- 测试应当能在内部重构后存活——它们描述行为，而非实现。如果一个测试在实现改变时不得不改，那它测的就是接口之外的东西。

# 改进代码库架构

浮现出架构上的摩擦，并提出**深化机会**——把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

这个命令_受_项目领域模型的_启发_，并建立在一套共享的设计词汇之上：

- 运行 `/codebase-design` 技能以获取架构词汇（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除测试、「接口即测试面」、「一个适配器 = 假想的接缝，两个 = 真实的接缝」）。在每条建议中精确使用这些术语——不要漂移成「component」「service」「API」或「boundary」。
- `CONTEXT.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录了这个命令不应重新翻案的决策。

## 流程

### 1. 探索

先阅读项目的领域术语表（`CONTEXT.md`）以及你所触及区域内的任何 ADR。

然后使用 Agent 工具、以 `subagent_type=Explore` 走查代码库。不要遵循僵化的启发式规则——有机地探索，并记下你在哪里感到摩擦：

- 理解一个概念在哪里需要在许多小模块之间来回跳转？
- 哪里的模块是**浅的**——接口几乎和实现一样复杂？
- 哪里的纯函数只是为了可测试性而被抽取出来，但真正的 bug 却藏在它们如何被调用之中（没有**locality**）？
- 哪里的紧耦合模块跨接缝泄漏？
- 代码库的哪些部分未经测试，或很难通过其当前接口来测试？

对你怀疑是浅的任何东西应用**删除测试**：删除它会让复杂度集中，还是只是把它挪个地方？「是的，会集中」才是你想要的信号。

### 2. 用 HTML 报告呈现候选项

把一个自包含的 HTML 文件写到 OS 临时目录，这样就不会有东西落进仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（在 Windows 上则是 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一个新文件。为用户打开它——Linux 上用 `xdg-open <path>`，macOS 上用 `open <path>`，Windows 上用 `start <path>`——并告诉他们绝对路径。

报告使用 **Tailwind via CDN** 做布局和样式，并在图/流/序列能可靠传达结构时使用 **Mermaid via CDN** 做图示。把 Mermaid 与手工制作的 CSS/SVG 视觉呈现混用——当关系呈图状时（调用图、依赖、序列）用 Mermaid，而当你想要更具编辑性的东西（质量图、剖面图、坍缩动画）时用手工搭建的 div/SVG。每个候选项都配一个**前/后可视化**。要有画面感。

对每个候选项，渲染一张卡片，包含：

- **文件**——涉及哪些文件/模块
- **问题**——为什么当前架构在造成摩擦
- **方案**——用朴实的英文描述会改变什么
- **收益**——用 locality 和 leverage 的角度来解释，以及测试会如何改善
- **前 / 后 图示**——并排、自绘，说明其浅薄以及深化
- **推荐强度**——`Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽章

在报告末尾放一个**首选推荐**区块：你会先着手哪个候选项以及为什么。

**领域用 CONTEXT.md 的词汇，架构用 `/codebase-design` 的词汇。** 如果 `CONTEXT.md` 定义了「Order」，就谈「Order intake 模块」——而不是「FooBarHandler」，也不是「Order 服务」。

**ADR 冲突**：如果某个候选项与现有 ADR 相抵触，只有在摩擦真实到足以让人重新审视该 ADR 时才把它浮现出来。在卡片里清楚地标记它（例如一个警告提示框：_「与 ADR-0007 相抵触——但值得重开，因为……」_）。不要罗列某个 ADR 所禁止的每一种理论上的重构。

完整的 HTML 脚手架、图示模式和样式指引见 [HTML-REPORT.md](HTML-REPORT.md)。

暂时**不要**提出接口。文件写完后，问用户：「这些当中你想探索哪一个？」

### 3. 拷问回路

一旦用户选定一个候选项，运行 `/grilling` 技能与他们一起走查设计树——约束、依赖、被深化模块的形状、接缝背后是什么、哪些测试得以存续。

副作用随着决策成形而就地发生——运行 `/domain-modeling` 技能以在推进过程中保持领域模型的最新状态：

- **要用一个不在 `CONTEXT.md` 中的概念来命名被深化的模块？** 把这个术语加进 `CONTEXT.md`。如果文件不存在就惰性创建。
- **在对话中磨锐了一个模糊的术语？** 当场更新 `CONTEXT.md`。
- **用户以一个起承重作用的理由否决了候选项？** 提议一个 ADR，措辞为：_「要我把它记为一条 ADR，以免未来的架构评审再次建议它吗？」_ 只有当这个理由确实会被未来的探索者需要、以避免再次建议同样的东西时才提议——跳过临时性的理由（「现在不值得做」）和不言自明的理由。
- **想为被深化的模块探索备选接口？** 运行 `/codebase-design` 技能，并使用它的「设计两次」并行子智能体模式。

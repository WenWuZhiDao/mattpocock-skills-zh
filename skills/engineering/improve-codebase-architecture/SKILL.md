# 改进代码库架构

暴露架构层面的摩擦，并提出**深化机会（deepening opportunities）**——把浅模块变成深模块的重构。目标是可测试性以及对 AI 的可导航性。

## 术语表

在每条建议中都要精确使用这些术语。语言保持一致正是关键所在——不要漂移成「组件（component）」「服务（service）」「API」或「边界（boundary）」。完整定义见 [LANGUAGE.md](LANGUAGE.md)。

- **Module（模块）** — 任何有接口和实现的东西（函数、类、包、切片）。
- **Interface（接口）** — 调用方使用该模块所必须知道的一切：类型、不变量、错误模式、顺序、配置。不仅仅是类型签名。
- **Implementation（实现）** — 内部的代码。
- **Depth（深度）** — 接口处的杠杆：小接口背后藏着大量行为。**Deep（深）** = 高杠杆。**Shallow（浅）** = 接口几乎和实现一样复杂。
- **Seam（缝）** — 接口所在之处；一个可以在不就地修改的情况下改变行为的地方。（用这个词，不要用「边界」。）
- **Adapter（适配器）** — 在某个缝处满足某接口的具体东西。
- **Leverage（杠杆）** — 调用方从深度中得到的东西。
- **Locality（局部性）** — 维护者从深度中得到的东西：变更、缺陷、知识都集中在同一处。

关键原则（完整列表见 [LANGUAGE.md](LANGUAGE.md)）：

- **删除测试（deletion test）**：设想删掉这个模块。如果复杂度消失了，它就是个传递层。如果复杂度在 N 个调用方处重新出现，那它就是物有所值的。
- **接口就是测试面（test surface）。**
- **一个适配器 = 假设的缝。两个适配器 = 真实的缝。**

本技能**受**项目领域模型的启发。领域语言为好的缝命名；ADR 记录了本技能不应重新争论的决策。

## 流程

### 1. 探索

先阅读项目的领域术语表，以及你要触及的区域中的任何 ADR。

然后用 Agent 工具配合 `subagent_type=Explore` 走查代码库。不要遵循僵硬的启发式规则——有机地探索，并记下你感到摩擦的地方：

- 哪里理解一个概念需要在许多小模块之间来回跳转？
- 哪里的模块是**浅的**——接口几乎和实现一样复杂？
- 哪里的纯函数只是为了可测试性被提取出来，但真正的缺陷却藏在它们的调用方式里（没有**局部性**）？
- 哪里紧耦合的模块跨越它们的缝泄漏？
- 代码库的哪些部分没有测试，或者通过当前接口很难测试？

对任何你怀疑是浅模块的东西施加**删除测试**：删掉它会让复杂度集中，还是只是搬个地方？「会，集中」就是你想要的信号。

### 2. 以 HTML 报告呈现候选项

把一个自包含的 HTML 文件写到操作系统的临时目录，这样不会有任何东西落进仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上是 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一份新文件。为用户打开它——Linux 上用 `xdg-open <path>`，macOS 上用 `open <path>`，Windows 上用 `start <path>`——并告诉他们绝对路径。

报告通过 **CDN 引入 Tailwind** 做布局和样式，并通过 **CDN 引入 Mermaid** 在图/流程/时序图能可靠传达结构的地方画图。把 Mermaid 与手工编写的 CSS/SVG 视觉元素混合使用——当关系是图状的（调用图、依赖、时序）时用 Mermaid，当你想要更具编辑感的东西（质量图、剖面图、坍缩动画）时用手工编写的 div/SVG。每个候选项都配一张**前后对比可视化**。要视觉化。

每个候选项使用与之前相同的模板，但渲染为一张卡片：

- **Files（文件）** — 涉及哪些文件/模块
- **Problem（问题）** — 当前架构为什么造成摩擦
- **Solution（方案）** — 用白话描述将会改变什么
- **Benefits（收益）** — 用局部性和杠杆来解释，以及测试会如何改善
- **Before / After diagram（前后对比图）** — 并排、定制绘制，展示浅薄之处和深化之后
- **Recommendation strength（推荐强度）** — `Strong`（强）、`Worth exploring`（值得探索）、`Speculative`（推测性）之一，渲染为徽章

报告以一个 **Top recommendation（首要推荐）** 小节结尾：你会先着手哪个候选项，以及为什么。

**领域用 CONTEXT.md 的词汇，架构用 [LANGUAGE.md](LANGUAGE.md) 的词汇。**如果 `CONTEXT.md` 定义了「Order」，就说「Order 接收模块」——而不是「FooBarHandler」，也不是「Order 服务」。

**ADR 冲突**：如果某个候选项与现有 ADR 矛盾，只在摩擦足够真实、值得重新审视该 ADR 时才提出它。在卡片中清楚标注（例如一个警告标注框：_「与 ADR-0007 矛盾——但值得重新讨论，因为……」_）。不要把某个 ADR 所禁止的每一种理论上的重构都列出来。

完整的 HTML 脚手架、图表样式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

现在还不要提出接口。文件写好后，问用户：「这些里面你想探索哪一个？」

### 3. 拷问循环

一旦用户选定一个候选项，就进入一段拷问式对话。与他们一起走查设计树——约束、依赖、深化模块的形状、缝背后是什么、哪些测试能存活。

随着决策成形，副作用就地发生：

- **把一个深化模块以 `CONTEXT.md` 中没有的概念来命名？**把该术语加入 `CONTEXT.md`——与 `/grill-with-docs` 同样的纪律（见 [CONTEXT-FORMAT.md](../grill-with-docs/CONTEXT-FORMAT.md)）。如果文件不存在就惰性创建。
- **在对话中锐化了一个模糊术语？**就地更新 `CONTEXT.md`。
- **用户以一个起承重作用的理由否决了候选项？**提议写一个 ADR，措辞为：_「要我把这记成一个 ADR 吗，这样未来的架构评审就不会再次建议它？」_只在这个理由确实会被未来的探索者用来避免重复建议同一件事时才提议——略过临时性理由（「现在不值得」）和不言自明的理由。见 [ADR-FORMAT.md](../grill-with-docs/ADR-FORMAT.md)。
- **想为深化模块探索备选接口？**见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。

<what-to-do>

围绕这个计划的每一个方面，对我进行毫不留情的拷问，直到我们达成共识。沿着设计树的每一个分支逐一走下去，一个接一个地解决各个决策之间的依赖关系。对于每个问题，给出你推荐的答案。

一次只问一个问题，在每个问题上等待反馈后再继续。

如果某个问题可以通过探索代码库来回答，那就去探索代码库。

</what-to-do>

## 领域意识

在探索代码库的过程中，也要留意现有的文档：

### 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则该仓库有多个上下文。这张映射图指明每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性地创建文件——只在你有内容要写的时候才创建。如果不存在 `CONTEXT.md`，在第一个术语被确定时创建一个。如果不存在 `docs/adr/`，在第一个 ADR 需要时创建它。

## 拷问过程中

### 对照术语表提出挑战

当用户使用的术语与 `CONTEXT.md` 中已有的语言冲突时，立即指出来。"你的术语表把 'cancellation' 定义为 X，但你似乎指的是 Y——到底是哪个？"

### 锐化模糊的语言

当用户使用含糊或一词多义的术语时，提出一个精确的规范术语。"你说的是 'account'——你指的是 Customer 还是 User？这是两个不同的东西。"

### 讨论具体场景

当正在讨论领域关系时，用具体场景来对其进行压力测试。设计一些能探测边界情况的场景，逼迫用户对概念之间的边界做到精确。

### 与代码交叉验证

当用户陈述某个东西如何工作时，检查代码是否与之一致。如果发现矛盾，把它摆出来："你的代码取消的是整个 Order，但你刚才说可以部分取消——到底哪个对？"

### 内联更新 CONTEXT.md

当一个术语被确定时，就地更新 `CONTEXT.md`。不要把这些攒着——在它们发生的时候就捕获下来。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应当完全不含实现细节。不要把 `CONTEXT.md` 当作规格说明、草稿本，或实现决策的存放处。它就是一个术语表，仅此而已。

### 谨慎地提议 ADR

只有当以下三点同时成立时，才提议创建 ADR：

1. **难以撤销**——日后改变主意的代价是有意义的
2. **缺少背景就令人费解**——未来的读者会想"他们为什么要这样做？"
3. **是真实权衡的结果**——确实存在多个备选方案，而你出于具体原因选择了其中一个

如果三点中缺了任何一点，就跳过这个 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。

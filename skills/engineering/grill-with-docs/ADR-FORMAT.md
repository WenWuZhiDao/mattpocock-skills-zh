# ADR 格式

ADR 存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

惰性地创建 `docs/adr/` 目录——只在第一个 ADR 需要时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们决定了什么，以及为什么。}
```

就这些。一个 ADR 可以只有一段。其价值在于记录下"一个决策被做出了"以及"为什么"——而不在于把各个章节填满。

## 可选章节

只在这些章节确实带来真正价值时才包含。大多数 ADR 都不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策会被重新审视时有用
- **Considered Options**——只在被否决的备选方案值得记住时
- **Consequences**——只在需要指出非显而易见的下游影响时

## 编号

扫描 `docs/adr/`，找到已有的最大编号，加一。

## 何时提议 ADR

以下三点必须同时成立：

1. **难以撤销**——日后改变主意的代价是有意义的
2. **缺少背景就令人费解**——未来的读者看着代码会想"他们到底为什么要这样做？"
3. **是真实权衡的结果**——确实存在多个备选方案，而你出于具体原因选择了其中一个

如果一个决策很容易撤销，就跳过它——反正你会撤销它。如果它并不令人费解，没人会想为什么。如果根本没有真正的备选方案，那么除了"我们做了显而易见的事"之外没什么可记录的。

### 哪些情况符合条件

- **架构形态。** "我们使用 monorepo。""写模型采用事件溯源，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而非同步 HTTP。"
- **带有锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库——只是那些要替换得花上一个季度的。
- **边界与范围决策。** "Customer 数据归 Customer 上下文所有；其他上下文只通过 ID 引用它。" 那些明确的"否"和"是"一样有价值。
- **对显而易见路径的有意偏离。** "我们用手写 SQL 而不是 ORM，因为 X。" 任何一个理性读者会假设相反做法的地方。这些能阻止下一个工程师去"修复"某个本是有意为之的东西。
- **代码中不可见的约束。** "出于合规要求我们不能用 AWS。""由于合作方 API 合约，响应时间必须低于 200ms。"
- **被否决的备选方案，当否决的理由不显而易见时。** 如果你考虑过 GraphQL 而出于微妙的原因选择了 REST，记录下来——否则半年后有人会再次提议用 GraphQL。

# Diagnose（诊断）

针对疑难 bug 的一套纪律。只有在明确给出理由时才跳过某些阶段。

在探索代码库时，使用项目的领域术语表来建立对相关模块的清晰心智模型，并查阅你所触及区域的 ADR。

## 阶段 1 — 构建反馈循环

**这才是这个技能的核心。** 其余一切都只是机械操作。如果你拥有一个快速、确定、可由 agent 运行的 bug 通过/失败信号，你就一定能找到原因——二分定位、假设验证和插桩，都只是在消费这个信号。如果你没有这个信号，盯着代码看再久也救不了你。

在这里要投入不成比例的精力。**要激进。要有创意。拒绝放弃。**

### 构建反馈循环的方式——大致按此顺序尝试

1. **失败的测试**，放在任何能触达该 bug 的接缝处——单元、集成、端到端。
2. **Curl / HTTP 脚本**，打到正在运行的开发服务器上。
3. **CLI 调用**，用固定的输入夹具，将 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/控制台/网络做断言。
5. **回放捕获的 trace。** 将真实的网络请求 / 载荷 / 事件日志存到磁盘；在隔离环境中通过代码路径回放它。
6. **用完即弃的测试架。** 启动系统的一个最小子集（一个服务、mock 掉依赖），用单次函数调用来触发 bug 代码路径。
7. **属性 / 模糊循环。** 如果 bug 表现为「有时输出错误」，跑 1000 个随机输入，寻找失败模式。
8. **二分定位测试架。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，把「在状态 X 启动、检查、重复」自动化，这样你就能用 `git bisect run` 跑它。
9. **差分循环。** 把同一个输入分别通过旧版本和新版本（或两套配置），对输出做 diff。
10. **HITL（人在回路）bash 脚本。** 最后手段。如果必须由人来点击，就用 `scripts/hitl-loop.template.sh` 来驱动*他们*，使循环依然保持结构化。捕获的输出会反馈给你。

构建出正确的反馈循环，bug 就修好了 90%。

### 对循环本身进行迭代

把循环当成一个产品来对待。一旦你有了*某个*循环，就问：

- 我能让它更快吗？（缓存初始化、跳过无关的初始化、缩小测试范围。）
- 我能让信号更锐利吗？（断言到具体症状上，而不是「没崩溃」。）
- 我能让它更确定吗？（固定时间、给 RNG 设种子、隔离文件系统、冻结网络。）

一个耗时 30 秒、时灵时不灵的循环，比没有循环强不了多少。一个 2 秒、确定的循环则是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发动作循环 100 次、并行化、加压、收窄时序窗口、注入 sleep。50% 概率出错的 bug 是可调试的；1% 则不行——不断提高复现率，直到它可调试为止。

### 当你确实无法构建循环时

停下来，明确说出这一点。列出你尝试过什么。向用户索要：(a) 能复现该问题的环境的访问权限，(b) 捕获到的产物（HAR 文件、日志转储、core dump、带时间戳的屏幕录像），或 (c) 添加临时生产环境插桩的许可。在没有循环的情况下，**不要**贸然进入提出假设阶段。

在你拥有一个自己信得过的循环之前，不要进入阶段 2。

## 阶段 2 — 复现

运行循环。亲眼看到 bug 出现。

确认：

- [ ] 循环产生的是**用户**所描述的那个失败模式——而不是恰好在附近的另一个失败。错的 bug = 错的修复。
- [ ] 该失败在多次运行中可复现（对于非确定性 bug，则在足够高的复现率下可复现，足以据此调试）。
- [ ] 你已经捕获了确切症状（错误信息、错误输出、缓慢的时序），以便后续阶段能验证修复确实针对它。

在复现 bug 之前，不要继续往下。

## 阶段 3 — 提出假设

在测试任何假设之前，先生成**3–5 个排好序的假设**。只生成单个假设会让你锚定在第一个看似合理的想法上。

每个假设都必须是**可证伪的**：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。"

如果你说不出这个预测，那这个假设就只是一种感觉——抛弃它或把它打磨清楚。

**在测试之前把这份排好序的列表展示给用户。** 他们往往拥有能立刻重排次序的领域知识（"我们刚刚对第 3 条做了一次部署"），或者知道哪些假设他们已经排除过了。便宜的检查点，巨大的时间节省。不要为此阻塞——如果用户离开了（AFK），就按你的排序继续。

## 阶段 4 — 插桩

每个探针都必须对应阶段 3 中的某个具体预测。**一次只改一个变量。**

工具优先级：

1. 如果环境支持，用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在区分各假设的边界处打**有针对性的日志**。
3. 绝不"把所有东西都打日志然后 grep"。

**给每条调试日志打上**一个唯一前缀，例如 `[DEBUG-a4f2]`。最后的清理就变成一次 grep。没打标签的日志会留存下来；打了标签的日志会被清除。

**性能分支。** 对于性能退化，日志通常是错的做法。改为：先建立一个基线测量（计时测试架、`performance.now()`、profiler、查询计划），然后二分定位。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

在修复**之前**写回归测试——但仅当存在一个**正确的接缝**时。

正确的接缝是指：测试能在调用点处触发**真实的 bug 模式**。如果唯一可用的接缝太浅（在 bug 需要多个调用者时却写了单调用者测试，或单元测试无法复现触发 bug 的那条调用链），那么在那里写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是一个发现。** 记下它。代码库的架构正在阻止这个 bug 被锁定。把这一点标记出来，留给下一阶段。

如果存在正确的接缝：

1. 把最小化的复现变成该接缝处的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化）的场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 复盘

在宣告完成之前必须做到：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录接缝缺失这一情况）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 该前缀）
- [ ] 用完即弃的原型已删除（或移到一个明确标记的调试位置）
- [ ] 最终被证明正确的那个假设已写入提交 / PR 信息中——这样下一个调试者能从中学习

**然后问：什么本可以预防这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、调用者纠缠、隐藏耦合），就把具体情况移交给 `/improve-codebase-architecture` 技能。**在**修复落地**之后**再给出建议，而不是之前——现在你掌握的信息比开始时多。

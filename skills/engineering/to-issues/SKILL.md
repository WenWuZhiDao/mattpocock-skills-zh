# 拆分为 Issue

使用垂直切片（曳光弹）将一份计划拆分成可被独立认领的 issue。

issue 跟踪器和 triage 标签词汇表应当已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容开展工作。如果用户以参数形式传入一个 issue 引用（issue 编号、URL 或路径），从 issue 跟踪器中获取它，并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索过代码库，那就探索一遍，以理解代码的当前状态。issue 的标题和描述应当使用项目的领域术语表词汇，并尊重你所触及区域内的 ADR。

### 3. 起草垂直切片

将计划拆分成**曳光弹**式的 issue。每个 issue 都是一个端到端贯穿**所有**集成层的细薄垂直切片，而**不是**某一层的水平切片。

切片可以是 'HITL'（需人工介入）或 'AFK'（无需人工）的。HITL 切片需要人工交互，比如架构决策或设计评审。AFK 切片可以在无人工交互的情况下实现并合并。在可能的情况下优先选择 AFK 而非 HITL。

<vertical-slice-rules>
- 每个切片都交付一条狭窄但**完整**、贯穿每一层（schema、API、UI、测试）的路径
- 一个完成的切片应能独立演示或验证
- 优先选择许多细薄的切片，而非少数厚重的切片
</vertical-slice-rules>

### 4. 向用户提问核对

将提议的拆分方案以编号列表的形式呈现。对每个切片，展示：

- **标题（Title）**：简短的描述性名称
- **类型（Type）**：HITL / AFK
- **被阻塞于（Blocked by）**：哪些其他切片（如有）必须先完成
- **覆盖的用户故事（User stories covered）**：本切片处理了哪些用户故事（如果源材料中有的话）

向用户提问：

- 粒度是否合适？（太粗 / 太细）
- 依赖关系是否正确？
- 是否应将某些切片合并或进一步拆分？
- 标记为 HITL 和 AFK 的切片是否正确？

反复迭代，直到用户认可这个拆分方案。

### 5. 将 issue 发布到 issue 跟踪器

对每个获批的切片，向 issue 跟踪器发布一个新的 issue。使用下面的 issue 正文模板。这些 issue 被视为已可供 AFK agent 处理，因此除非另有指示，发布时请打上正确的 triage 标签。

按依赖顺序（先发布阻塞者）发布 issue，这样你就能在 "Blocked by" 字段中引用真实的 issue 标识符。

<issue-template>
## 父级（Parent）

指向 issue 跟踪器上父 issue 的引用（如果源是一个已有的 issue，否则省略本节）。

## 要构建什么（What to build）

对本垂直切片的简洁描述。描述端到端的行为，而非逐层的实现。

避免具体的文件路径或代码片段——它们很快就会过时。例外：如果某个原型产出了一段比文字更精确地编码了某项决策的片段（状态机、reducer、schema、类型形状），就把它内联在这里，并简要说明它来自一个原型。修剪到决策密集的部分——不是一个可运行的演示，只是重要的片段。

## 验收标准（Acceptance criteria）

- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3

## 被阻塞于（Blocked by）

- 指向阻塞工单的引用（如有）

或者，如果没有阻塞者，则填 "None - can start immediately"（无 - 可立即开始）。

</issue-template>

不要关闭或修改任何父 issue。

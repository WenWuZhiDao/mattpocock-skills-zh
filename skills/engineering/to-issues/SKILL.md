# To Issues

使用垂直切片（曳光弹）将计划拆分为可独立认领的 issue（问题）。

问题追踪器和分诊标签词汇应该已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容出发工作。如果用户以参数形式传入一个 issue 引用（issue 编号、URL 或路径），从问题追踪器获取它，并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索过代码库，请这样做以理解代码的当前状态。issue 标题和描述应使用项目的领域术语表词汇，并尊重你所触及区域内的 ADR。

寻找机会预先重构（prefactor）代码，使实现更容易。“先让改动变容易，再做这个容易的改动。”

### 3. 起草垂直切片

将计划拆分为**曳光弹** issue。每个 issue 都是一个贯穿所有集成层、端到端的薄垂直切片，而不是单一层的水平切片。

<vertical-slice-rules>

- 每个切片交付一条穿过每一层（schema、API、UI、测试）的狭窄但**完整**的路径
- 完成的切片本身可演示或可验证
- 任何预重构都应先完成

</vertical-slice-rules>

### 4. 拷问用户

以带编号的列表呈现拟定的拆分方案。对每个切片，展示：

- **标题**：简短的描述性名称
- **被阻塞于**：哪些其他切片（如有）必须先完成
- **涵盖的用户故事**：这个切片处理哪些用户故事（如果源材料中有）

问用户：

- 粒度感觉合适吗？（太粗 / 太细）
- 依赖关系正确吗？
- 是否应合并或进一步拆分某些切片？

反复迭代，直到用户批准拆分方案。

### 5. 将 issue 发布到问题追踪器

对每个获批的切片，向问题追踪器发布一个新 issue。使用下面的 issue 正文模板。这些 issue 被视为已为 AFK 智能体准备就绪，因此除非另有指示，请以正确的分诊标签发布它们。

按依赖顺序发布 issue（先发布阻塞者），以便你能在“被阻塞于”字段中引用真实的 issue 标识符。

<issue-template>
## Parent

指向问题追踪器上父 issue 的引用（如果来源是一个已有的 issue，否则省略本节）。

## What to build

这个垂直切片的简明描述。描述端到端的行为，而不是逐层的实现。

避免使用具体的文件路径或代码片段——它们会很快过时。例外：如果某个原型产出了一个比散文更精确地编码了某项决策的片段（状态机、reducer、schema、类型形态），把它内联在此，并简要注明它来自原型。裁剪到富含决策的部分——不是一个可运行的演示，只是重要的片段。

## Acceptance criteria

- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3

## Blocked by

- 指向阻塞工单的引用（如有）

或者，如果没有阻塞者，则写 "None - can start immediately"。

</issue-template>

不要关闭或修改任何父 issue。

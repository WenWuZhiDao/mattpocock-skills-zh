# 设计两遍（Design It Twice）

当用户想为某个选定的深化候选项探索备选接口时，使用这个并行子 agent 模式。基于「Design It Twice」（Ousterhout）——你的第一个想法不太可能是最好的那个。

使用 [SKILL.md](SKILL.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

在派发子 agent 之前，为选定的候选项写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖的依赖项，以及它们属于哪一类（见 [DEEPENING.md](DEEPENING.md)）
- 一份粗略的示意性代码草图，用来把约束落到实处——不是一份提案，只是让约束变具体的一种方式

把这个展示给用户，然后立即进入第 2 步。用户在子 agent 并行工作时阅读和思考。

### 2. 派发子 agent

并行派发 3 个以上的子 agent。每个都必须为这个深化后的模块产出一个**截然不同**的接口。

用一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖分类、接缝背后是什么）提示每个子 agent。这份简报独立于第 1 步中面向用户的问题空间说明。给每个 agent 一个不同的设计约束：

- Agent 1：「把接口最小化——目标是最多 1–3 个入口点。让每个入口点的杠杆最大化。」
- Agent 2：「把灵活性最大化——支持许多用例和扩展。」
- Agent 3：「为最常见的调用方优化——让默认情形变得微不足道。」
- Agent 4（若适用）：「围绕端口与适配器（ports & adapters）来设计跨接缝的依赖。」

在简报中同时包含 [SKILL.md](SKILL.md) 的词汇和 CONTEXT.md 的词汇，让每个子 agent 都能用与架构语言和项目领域语言一致的方式命名事物。

每个子 agent 输出：

1. 接口（类型、方法、参数——外加不变量、顺序、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现藏在接缝背后的东西
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆在哪里高，在哪里薄

### 3. 呈现并比较

依次呈现各个设计，让用户逐一吸收，然后用散文把它们比较一番。按**深度**（接口处的杠杆）、**局部性**（变化集中在哪里）和**接缝位置**来对比。

比较之后，给出你自己的建议：你认为哪个设计最强以及为什么。如果不同设计里的元素能很好地组合，就提出一个混合方案。要有主见——用户想要的是一个强有力的判断，而不是一份菜单。

# Design It Twice

当用户想为选定的深化候选者探索备选接口时，使用这个并行子智能体模式。基于 "Design It Twice"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇——**module（模块）**、**interface（接口）**、**seam（接缝）**、**adapter（适配器）**、**leverage（杠杆）**。

## 流程

### 1. 框定问题空间

在派生子智能体之前，为选定的候选者写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖的依赖，以及它们落入哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一份粗略的示意性代码草图，用以锚定这些约束——不是提案，只是把约束具体化的方式

把这个展示给用户，然后立即进入第 2 步。用户阅读和思考的同时，子智能体在并行工作。

### 2. 派生子智能体

用 Agent 工具并行派生 3 个以上子智能体。每个都必须为深化后的模块产出一个 **根本不同** 的接口。

用一份单独的技术简述提示每个子智能体（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝后面坐落着什么）。该简述独立于第 1 步中面向用户的问题空间说明。给每个智能体一个不同的设计约束：

- 智能体 1："最小化接口——目标是最多 1–3 个入口点。最大化每个入口点的杠杆。"
- 智能体 2："最大化灵活性——支持众多用例和扩展。"
- 智能体 3："为最常见的调用方优化——让默认情况变得微不足道。"
- 智能体 4（如适用）："围绕 ports & adapters 设计跨接缝依赖。"

在简述中同时包含 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇，这样每个子智能体命名事物时都与架构语言和项目的领域语言保持一致。

每个子智能体输出：

1. 接口（类型、方法、参数——外加不变式、顺序、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现在接缝后面藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆在哪里高，在哪里薄

### 3. 呈现与比较

依次呈现各个设计，让用户能逐一吸收，然后用文字比较它们。从 **depth（深度，接口处的杠杆）**、**locality（局部性，变化集中在何处）** 和 **接缝的放置** 三方面对比。

比较之后，给出你自己的推荐：你认为哪个设计最强以及为什么。如果来自不同设计的元素能很好地组合，就提出一个混合方案。要有主见——用户想要一个强有力的判断，而不是一份菜单。

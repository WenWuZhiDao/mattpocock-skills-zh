# Deepening

在给定依赖的情况下，如何安全地深化一簇浅模块。假定你已掌握 [SKILL.md](SKILL.md) 中的词汇——**module（模块）**、**interface（接口）**、**seam（接缝）**、**adapter（适配器）**。

## 依赖类别

在评估一个深化候选者时，对其依赖分类。类别决定了深化后的模块如何跨接缝测试。

### 1. In-process（进程内）

纯计算、内存态、无 I/O。总是可深化——合并这些模块并直接通过新接口测试。不需要适配器。

### 2. Local-substitutable（可本地替身）

拥有本地测试替身的依赖（用 PGLite 替 Postgres、内存文件系统）。若替身存在则可深化。深化后的模块用运行在测试套件中的替身来测试。接缝是内部的；模块的外部接口处没有端口。

### 3. Remote but owned（远程但自有，Ports & Adapters）

跨网络边界的你自己的服务（微服务、内部 API）。在接缝处定义一个 **port（端口，即接口）**。深模块拥有逻辑；传输作为一个 **adapter（适配器）** 注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

推荐形态：*"在接缝处定义一个端口，为生产实现一个 HTTP 适配器、为测试实现一个内存适配器，这样即便逻辑部署在跨网络的多处，它仍坐落于一个深模块中。"*

### 4. True external（真正外部，Mock）

你不掌控的第三方服务（Stripe、Twilio 等等）。深化后的模块把外部依赖作为注入的端口接收；测试提供一个 mock 适配器。

## 接缝准则

- **一个适配器意味着一个假想的接缝。两个适配器才意味着一个真实的接缝。** 除非至少有两个适配器站得住脚（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是间接层。
- **内部接缝 vs 外部接缝。** 一个深模块可以既有内部接缝（对其实现私有，供它自己的测试使用），也有其接口处的外部接缝。不要仅仅因为测试用到它们就把内部接缝通过接口暴露出去。

## 测试策略：替换，别叠加

- 一旦有了深化后模块接口处的测试，浅模块上的旧单元测试就成了废物——删掉它们。
- 在深化后模块的接口处编写新测试。**接口就是测试面**。
- 测试断言通过接口观察到的结果，而非内部状态。
- 测试应当熬得过内部重构——它们描述行为，而非实现。如果一个测试必须在实现变化时随之改变，那它就是在越过接口测试。

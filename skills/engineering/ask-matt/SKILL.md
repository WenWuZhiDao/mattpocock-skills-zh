# Ask Matt

你不会记得每一个技能，所以直接问。

**flow（流程）** 是穿过各技能的一条路径。大多数路径沿着一条 **主流程** 前行，另有两个 **on-ramp（引入口）** 汇入其中。其余的要么是独立的，要么是在底层运行的词汇层。

## 主流程：想法 → 交付

大多数工作走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** — 通过访谈打磨想法。当你 **有一个代码库** 时从这里开始：它是有状态的，会把学到的东西保留在 `CONTEXT.md` 和 ADR 中。（没有代码库？用 `/grill-me`——见 Standalone。两者都运行同一个 `/grilling` 原语；`grill-with-docs` 是会留下书面记录的那一个。）
2. **分支——你能在对话中把每个问题都敲定吗？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、你必须亲眼看到的 UI），就绕道去做一个原型，两个方向都由 **`/handoff`** 搭桥（见 Crossing sessions）：
   - **`/handoff`** 出去，然后针对那个文件开一个全新会话，
   - **`/prototype`** 用用后即弃的代码回答该问题，
   - **`/handoff`** 把你学到的东西带回来，并在原始的想法线程中引用它。
3. **分支——这是一个跨多会话的构建吗？**
   - **是** → **`/to-prd`**（把线程变成 PRD）→ **`/to-issues`**（把 PRD 拆成可独立领取的 issue）。因为这些 issue 是独立的，所以 **在每个之间清空上下文**：为每个 issue 开一个全新会话，并通过把 PRD 和要处理的那一个 issue 传给它来启动 **`/implement`**。
   - **否** → 就在这里、在同一个上下文窗口中运行 **`/implement`**。

   无论哪种方式，**`/implement`** 都会通过内部驱动 **`/tdd`** 来构建每个 issue——一次一个红-绿切片——然后在提交前运行 **`/code-review`**（对 diff 进行 Standards + Spec 双轴审查）来收尾。当你只想在没有完整规格的情况下以测试优先的方式构建一个具体行为时，单独调用 **`/tdd`**；当你想针对某个固定点审查一个分支或 PR 时，单独调用 **`/code-review`**。

### 上下文卫生

把第 1–3 步保持在 **一个不间断的上下文窗口** 中——在 `/to-issues` 之前不要压缩或清空——这样拷问、PRD 和 issue 都建立在同一套思考之上。之后每个 `/implement` 从头开始，基于 issue 工作。

对此的限制是 **[smart zone（智能区）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的那个窗口（在最先进模型上约 120k tokens）。如果某个会话在 `/to-issues` 之前就逼近它，不要在退化状态下硬撑——用 `/handoff` 并在一个全新线程中继续。

## On-ramps

一个会产生工作的起始情境，随后汇入主流程。

- **bug 和请求堆积起来** → **`/triage`**。它让 issue 在分诊角色间流转，产出可供智能体处理的 issue，供 **`/implement`** 之后领取。

  分诊只针对 **不是你创建的** issue——bug 报告、进来的功能请求，任何原始到达的东西。`/to-issues` 产出的 issue 已经可供智能体处理，所以 **不要对它们做分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。针对疑难的那些：第一眼看不出的 bug、间歇性的不稳定、在两个已知良好状态之间悄悄溜进来的回归。在拥有一个 **紧密的反馈回路**（一条已经能对 *这个* bug 变红的命令）之前，它拒绝空谈理论——然后用回归测试来修复。当真正的发现是「没有好的接缝来锁定这个 bug」时，它的事后复盘会移交给 **`/improve-codebase-architecture`**。

## 代码库健康

不是功能工作——是保养。

- **`/improve-codebase-architecture`** — 每当你有空闲时间、想让代码库保持适合智能体运作时运行。它会浮现 **深化机会**；选中一个 _会生成一个想法_，你可以把它带入主流程的 `/grill-with-docs` 处。它是找出候选者的普查；**`/codebase-design`**（下文）则是你设计所选那个的工作台。

## 底层的词汇

两个在其他技能 *之下* 运行的 model-invoked 参考——各自是其词汇的单一事实来源。当问题出在 **词语** 而非流程上时，直接调用它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`** — 打磨项目的 *领域* 语言：挑战一个模糊的术语、厘清一个被过载的词（"account" 同时干着三份活）、把一个难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动的、用来把 `CONTEXT.md` 保持为干净词汇表的主动准则。
- **`/codebase-design`** — 用于设计模块 *形态* 的深模块词汇（module、interface、depth、seam、adapter、leverage、locality）：在一个干净的接缝后、用小接口托起大量行为。`/tdd` 和 `/improve-codebase-architecture` 都讲这门语言。

## Crossing sessions

- **`/handoff`** — 当一个线程满了，或你需要分岔出去（例如进入一个 `/prototype` 会话）时，它把对话压缩成一个 markdown 文件。你不在原处继续——而是 **开一个新会话并引用那个文件** 来把上下文带过去。它是上下文窗口之间的桥梁，双向皆可。当你想要一个 **全新会话**、但需要 **保留当前对话** 时使用它。
- **`/compact`**（内置）— 留在 **同一个对话** 里，让较早的轮次被摘要。在 **阶段之间有意的间断处** 使用它，此时你不介意丢失逐字的历史。不要在阶段中途压缩——智能体可能会迷失方向。`/handoff` 分岔；`/compact` 继续。

## Standalone

完全在主流程之外。

- **`/grill-me`** — 与 `/grill-with-docs` 同样不留情面的访谈，但用于你 **没有代码库** 的时候。无状态：它不在本地保存任何东西，不构建 `CONTEXT.md`。当你要打磨任何不存在于仓库中的计划或设计时调用它。
- **`/prototype`** — 一个小小的、用后即弃的程序，回答一个设计问题：这个状态模型感觉对不对，或这个 UI 应该长什么样。从第一天起就用后即弃——留下答案，删掉代码。它是主流程第 2 步中的绕道，但任何时候一个设计问题在纸面上难以敲定时都可以调用。
- **`/teach`** — 跨多个会话学习一个概念，把当前目录当作有状态的工作区。
- **`/writing-great-skills`** — 关于如何写好和编辑技能的参考。

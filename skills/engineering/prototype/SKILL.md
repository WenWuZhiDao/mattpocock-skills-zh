# 原型

原型是**回答一个问题的一次性代码**。问题决定了它的形态。

## 选择一条分支

从用户的提示、周围的代码，或者在用户在场时通过询问，识别正在回答的是哪个问题：

- **「这套逻辑 / 状态模型感觉对吗？」** → [LOGIC.md](LOGIC.md)。构建一个微型的交互式终端应用，把状态机推过那些在纸面上难以推理的情形。
- **「这东西应该长什么样？」** → [UI.md](UI.md)。在单条路由上生成若干个截然不同的 UI 变体，通过一个 URL search 参数和一个悬浮的底部栏来切换。

这两条分支产出的产物非常不同——选错会浪费整个原型。如果问题确实模棱两可且联系不到用户，就默认选与周围代码更匹配的那条分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部声明这个假设。

## 两者通用的规则

1. **从第一天起就是一次性的，并被明确标注为一次性。** 把原型代码放在它实际会被使用的地方附近（紧挨着它所要原型化的模块或页面），这样上下文才明显——但给它起个名字，让随手翻看的读者一眼就能看出它是原型、而非生产代码。对于一次性的 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令即可运行。** 无论项目现有的任务运行器支持什么——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够不假思索地启动它。
3. **默认不做持久化。** 状态存在内存里。持久化是原型正在_检验_的东西，而不是它应当依赖的东西。如果问题明确涉及数据库，就命中一个临时（scratch）DB 或一个带明确「PROTOTYPE — wipe me」名字的本地文件。
4. **跳过打磨。** 没有测试，除了让原型_可运行_所必需的之外没有错误处理，没有抽象。目的是快速学到点东西，然后删掉它。
5. **把状态暴露出来。** 每次动作之后（逻辑）或每次变体切换时（UI），打印或渲染出全部相关状态，让用户能看到发生了什么变化。
6. **完成后删除或吸收。** 当原型回答了它的问题，要么删掉它，要么把已验证的决策折叠进真实代码——不要让它烂在仓库里。

## 完成之后

从原型里唯一值得保留的是那个_答案_。把它连同它所回答的问题一起，捕获到某个持久的地方（commit 消息、ADR、issue，或原型旁边的一个 `NOTES.md`）。如果用户在场，这次捕获就是一次快速对话；如果不在，就留下占位符，好让他们（或下一轮的你）在删掉原型之前填上结论。

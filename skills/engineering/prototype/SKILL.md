# 原型（Prototype）

原型是**用来回答一个问题的、用完即弃的代码**。问题决定了它的形态。

## 选择一个分支

判断要回答的是哪一类问题——从用户的提示、周围的代码，或者在用户在场时直接询问：

- **"这套逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个小巧的交互式终端应用，把状态机推过那些在纸面上难以推理的情形。
- **"这东西应该长什么样？"** → [UI.md](UI.md)。在同一个路由上生成几个截然不同的 UI 变体，通过 URL 查询参数和一个悬浮底栏进行切换。

这两个分支产出的工件截然不同——选错会让整个原型白做。如果问题确实含糊不清而又联系不上用户，就默认选择更贴合周围代码的那个分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两个分支通用的规则

1. **从第一天起就是一次性的，并明确标记为如此。** 把原型代码放在它实际会被用到的地方附近（紧挨着它要为之做原型的模块或页面），让上下文一目了然——但要给它起个名字，让随手浏览的人能看出这是原型而非生产代码。对于一次性的 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令即可运行。** 用项目现有任务运行器支持的任何方式——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能不假思索地把它跑起来。
3. **默认不做持久化。** 状态存在内存里。持久化正是原型要去**检验**的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，就连到一个临时数据库或本地文件，并起个清晰的名字，比如 "PROTOTYPE — wipe me"。
4. **跳过打磨。** 不写测试，除了让原型能**跑起来**之外不做错误处理，不做抽象。目标是快速学到点东西，然后删掉。
5. **暴露状态。** 在每次操作之后（逻辑）或每次切换变体时（UI），打印或渲染出全部相关状态，让用户能看到发生了什么变化。
6. **完成后删除或吸收。** 当原型回答完它的问题后，要么删掉它，要么把验证过的决策折叠进真实代码——别让它烂在仓库里。

## 完成之后

原型唯一值得保留的就是那个**答案**。把它连同它所回答的问题一起，记录到某个持久的地方（提交信息、ADR、issue，或紧挨着原型的 `NOTES.md`）。如果用户在场，这次记录就是一次简短对话；如果不在，就留下占位，让他们（或下一轮的你）在删除原型之前填上结论。

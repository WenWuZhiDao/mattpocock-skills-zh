# 逻辑原型

一个单一、自包含的 HTML 文件——一个**可分享的演示**——让任何人通过点击按钮来驱动一个状态模型。当问题是关于**业务逻辑、状态转换或数据形状**时使用它——那种在纸上看起来合理、但只有当你把它推过真实用例时才感觉不对劲的东西。

因为它是一个无需安装任何东西的单文件，你可以把它交给非开发者——设计师、PM、领域专家——让他们自己去感受这个模型。所以它说的是他们的语言，而不是代码的语言。

## 什么时候这是对的形状

- 「我不确定这个状态机能不能处理先 X 后 Y 的边界情况。」
- 「这个数据模型真的能让我表示……那种情况吗？」
- 「我想在动手写之前先感受一下这个 API 该长什么样。」
- 任何有人想**按按钮并观察状态变化**的场合。

如果问题是「这该长什么样」——分支选错了。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，写下你在原型化的是什么状态模型、什么问题。一段话，放在演示的顶部（在一段可见的引言里，不只是一条注释）。一个回答了错误问题的逻辑原型是纯粹的浪费——把问题写明确，好让它以后能被核对，无论用户是现在盯着看还是 AFK 之后再回来看。

### 2. 把逻辑隔离在一个可移植的模块里

把真正的逻辑——那个在回答问题的部分——放在单个 `<script>` 块里，写成一个小而纯的模块，以后可以被整块拿出来放进真实代码库。它周围的页面是用完即弃的；这个模块不是。

对的形状取决于问题：

- **一个纯 reducer** — `(state, action) => state`。当 action 是离散事件、state 是单个值时合适。
- **一个状态机** — 显式的状态和转换。当「此刻到底哪些 action 是合法的」是问题的一部分时合适。
- **一小组纯函数**，作用于一个普通数据类型之上。当没有隐含的当前状态时——只有变换——合适。
- **一个带清晰方法面的类或模块**，当逻辑确实拥有持续的内部状态时。

挑选最契合所问问题的那个形状，*而不是*最容易接到页面上的那个。保持它是纯的：没有 DOM、没有 `document`、没有伸进它内部的按钮处理器。页面调用它；没有东西反向流动。这正是让原型在自己生命周期之外仍有用的东西：一旦问题被回答，经过验证的 reducer / 状态机 / 函数集就能自行提升进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS——没有框架、没有打包器、没有服务器，一切内联，这样它双击就打开、被到处邮件转发也不出问题。任何人都应该能通过打开它来运行它。

为非开发者而写。每个标签都用**领域语言**，而非代码——按钮和状态读起来像业务，而非像 reducer。用平实的话解释正在发生什么。

以清晰的层次自上而下布局：

1. **标题和一行说明**，讲这个演示让你探索什么（第 1 步里的问题）。
2. **当前状态** — 全部相关状态，渲染成一个可读的面板（带标签的字段，不是原始 JSON 转储），每次点击后重新渲染，让变化可见。在有助于非开发者跟上的地方，标出刚刚变了什么。
3. **自由玩耍按钮** — 每个 action 一个按钮，始终可用，这样任何人都能以任意顺序戳这个模型。每次点击派发它的 action 并重新渲染状态。
4. **引导式演练** — 一组**场景**，每个场景一个标签页。每个标签页里有一段简短的平实语言描述，讲这个场景——它设置的情形以及要留意什么——下面则是该场景要按的、排好序的**按钮**。每一步都是一个真实按钮：点击它执行那个 action 并移动到下一步。开始一个演练会重置到一个已知的初始状态，这样场景每次都以同样的方式运行。

选择那些能展示别扭情形的场景——顺利路径、一个棘手的边界情况、一次本该非法的尝试——就是那些在纸上难以推理的情形。

保持它漂亮但克制：干净的排版、宽裕的留白、一个强调色。没有动画、没有噱头——没有任何跟状态和按钮争抢注意力的东西。

### 4. 交出去

把文件发给他们，或为他们打开。他们会在有空时点过这些演练并自由玩耍；有意思的时刻是他们说「等等，这不该可能」或「咦，我以为 X 会不一样」——那些是*想法*里的 bug，而这正是全部意义所在。如果他们想要新的 action 或新的场景，就加上。原型会演化。

### 5. 捕获答案和原型

一旦原型回答了它的问题，就捕获答案，然后按 [SKILL](SKILL.md) 所述的方式捕获原型。逻辑专属的映射：经过验证的 reducer / 状态机 / 函数集提升进真实模块（决策被吸收）；HTML 外壳随行搭上那个把原型作为一手来源保留的用完即弃分支——而由于它是一个自包含的单文件，它在那里始终轻松可重新运行。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要把它接到真实数据库。** 用内存状态，除非问题恰恰是关于持久化的。
- **不要泛化。** 别搞「万一以后我们想支持 X 呢」。原型只回答一个问题。
- **不要把逻辑和页面糊在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可提升。把页面保持为纯模块之上的一层薄外壳。
- **不要动用框架、打包器或服务器。** 一个收件人双击的文件；一个 React 应用或一个开发服务器会破坏「可分享」。
- **不要把 HTML 外壳带进生产。** 页面是为手工点击而优化的。它背后的逻辑模块才是值得保留的部分。

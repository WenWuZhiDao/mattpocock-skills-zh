# Logic Prototype

一个微型的交互式终端应用，让用户亲手驱动一个状态模型。当问题关乎**业务逻辑、状态转换或数据形态**时使用它——就是那种在纸面上看起来合理、但只有把它推过真实用例才会觉得不对劲的东西。

## 什么时候这是对的形态

- "我不确定这个状态机能不能处理先 X 后 Y 的边界情况。"
- "这个数据模型真的能让我表示……那种情况吗？"
- "我想在动手写之前先摸清这个 API 应该长什么样。"
- 任何用户想要**按按钮并观察状态变化**的场景。

如果问题是"这东西应该长什么样"——分支选错了。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，写下你正在为什么状态模型、为回答什么问题做原型。一段话，放在原型的 README 里或文件顶部的一条注释里。一个回答了错误问题的逻辑原型纯属浪费——把问题写明确，以便之后可以核对，无论用户此刻是否在看，还是稍后 AFK 再回来看。

### 2. 选择语言

用宿主项目所用的任何语言。如果项目没有明显的运行时（例如一个文档仓库），就问。

在工具方面匹配项目既有的约定——不要仅仅为了原型而引入一个新的包管理器或运行时。

### 3. 把逻辑隔离到一个可移植的模块中

把真正的逻辑——回答问题的那部分——放在一个小而纯的接口之后，以便之后可以整体抽出、放进真实代码库。围绕它的 TUI 是用完即弃的；逻辑模块则不应如此。

正确的形态取决于问题：

- **一个纯 reducer** —— `(state, action) => state`。当动作是离散事件、状态是单个值时适用。
- **一个状态机** —— 显式的状态与转换。当"此刻究竟哪些动作是合法的"本身就是问题的一部分时适用。
- **一小组纯函数**，作用于一个朴素的数据类型。当不存在隐式的当前状态——只有变换——时适用。
- **一个具有清晰方法面的类或模块**，当逻辑确实拥有持续的内部状态时。

选择最契合所问问题的那种形态，而*不是*最容易接到 TUI 上的那种。保持纯粹：没有 I/O，没有终端代码，没有用于控制流的 `console.log`。TUI 导入它并调用它；没有任何东西朝反方向流动。

这正是使原型在自身寿命之外仍然有用的原因：问题回答完后，经过验证的 reducer / 状态机 / 函数集可以独立地抬进真实模块。

### 4. 构建能暴露状态的最小 TUI

把它构建成一个**轻量 TUI**——每一个 tick 都清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价物）并重新渲染整个画面。用户应始终看到一个稳定的视图，而不是一个不断增长的滚动回溯。

每一帧有两部分，按此顺序：

1. **当前状态**，美观打印且便于 diff（每字段一行，或格式化的 JSON）。字段名或小节标题用**粗体**，不太重要的上下文（时间戳、ID、派生值）用**暗淡（dim）**。原生 ANSI 转义码即可——`\x1b[1m` 粗体、`\x1b[2m` 暗淡、`\x1b[0m` 重置。除非项目里已有样式库，否则无需引入。
2. **键盘快捷键**，列在底部：`[a] add user  [d] delete user  [t] tick clock  [q] quit`。键加粗、描述暗淡，或反之——怎么读着清爽就怎么来。

行为：

1. **初始化状态**——单个内存中的对象/结构体。启动时渲染第一帧。
2. **一次读取一个按键（或一行）**，分派给一个修改状态的处理器。
3. 每个动作后**重新渲染**整帧——不要追加，要替换。
4. **循环直到退出。**

整帧应能容纳在一屏之内。

### 5. 让它能用一条命令运行

在项目既有的任务运行器（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）中加一个脚本。用户应运行 `pnpm run <prototype-name>` 或等价命令——绝不需要记住某个路径。

如果宿主项目没有任务运行器，就把命令放在原型 README 的顶部。

### 6. 移交

把运行命令交给用户。他们会自己驱动它；有意思的时刻是当他们说"等等，这不应该可能"或"咦，我以为 X 会不一样"——那些正是*想法*里的 bug，而这正是整件事的意义所在。如果他们想加新动作，就加。原型会演进。

### 7. 沉淀答案与原型

一旦原型回答了它的问题，先沉淀答案，然后按 [SKILL](SKILL.md) 所述的方式沉淀原型。逻辑特有的对应关系是：经过验证的 reducer / 状态机 / 函数集抬进真实模块（决策被吸收）；TUI 外壳一并搭车进入那个把原型作为一手来源保留下来的用完即弃分支。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要接到真实数据库。** 使用内存存储，除非问题专门关乎持久化。
- **不要泛化。** 不要"万一以后想支持 X 呢"。原型只回答一个问题。
- **不要把逻辑和 TUI 糊在一起。** 如果 reducer / 状态机引用了 `console.log`、提示或终端转义码，它就不再可移植了。把 TUI 保持为纯模块之上的一层薄外壳。
- **不要把 TUI 外壳发进生产。** 外壳是为从终端手动驱动而优化的。它背后的逻辑模块才是值得留下的部分。

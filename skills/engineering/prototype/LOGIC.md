# 逻辑原型（Logic Prototype）

一个微型的交互式终端应用，让用户亲手驱动一个状态模型。当问题关乎**业务逻辑、状态转换或数据形态**时使用它——这类东西在纸面上看起来合理，但只有把它推过真实用例时才会感觉到不对劲。

## 什么时候这是正确的形态

- "我不确定这个状态机能不能处理先 X 后 Y 的边界情形。"
- "这个数据模型真的能让我表达……的情形吗"
- "我想在动手写之前先摸清这个 API 应该长什么样。"
- 任何用户想**按按钮、看着状态变化**的场景。

如果问题是"这东西应该长什么样"——选错分支了。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，先写下你要为之做原型的是哪个状态模型、哪个问题。一段话即可，写在原型的 README 里或文件顶部的注释里。回答错问题的逻辑原型纯属浪费——把问题写明确，以便日后核对，无论用户现在是否在看，还是离开后再回来看。

### 2. 选择语言

用宿主项目所用的语言。如果项目没有明显的运行时（比如一个文档仓库），就询问。

在工具方面要匹配项目已有的约定——不要仅仅为了原型就引入新的包管理器或运行时。

### 3. 把逻辑隔离到一个可移植的模块里

把真正的逻辑——也就是回答问题的那部分——放在一个小巧、纯粹的接口背后，将来可以把它拎出来直接放进真实代码库。包裹在它外面的 TUI 是一次性的；逻辑模块则不应是。

正确的形态取决于问题：

- **一个纯 reducer**——`(state, action) => state`。当动作是离散事件、状态是单一值时适用。
- **一个状态机**——显式的状态与转换。当"此刻到底哪些动作是合法的"也是问题的一部分时适用。
- **一组作用于普通数据类型的纯函数**。当不存在隐式的当前状态、只有一些变换时适用。
- **一个有清晰方法面的类或模块**，当逻辑确实拥有持续的内部状态时适用。

挑选最契合所提问题的形态，**而非**最容易接到 TUI 上的那个。保持它纯粹：没有 I/O，没有终端代码，不用 `console.log` 来控制流程。TUI 导入它并调用进去；不存在反方向的数据流。

这正是让原型在自身生命周期之外仍然有用的原因。当问题被回答后，验证过的 reducer / 状态机 / 函数集就能被拎进真实模块——而 TUI 外壳被删掉。

### 4. 构建能暴露状态的最小 TUI

把它做成一个**轻量 TUI**——每一帧都清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价物），然后重绘整个画面。用户应当始终看到一个稳定的视图，而不是不断增长的回滚历史。

每一帧有两个部分，按此顺序：

1. **当前状态**，美化打印且便于比对（每行一个字段，或格式化的 JSON）。字段名或区块标题用**加粗**，次要的上下文（时间戳、ID、派生值）用**暗淡**。原生 ANSI 转义码即可——`\x1b[1m` 加粗，`\x1b[2m` 暗淡，`\x1b[0m` 重置。除非项目里已经有样式库，否则没必要引入。
2. **键盘快捷键**，列在底部：`[a] add user  [d] delete user  [t] tick clock  [q] quit`。键加粗、描述暗淡，或反过来——怎么清晰怎么来。

行为：

1. **初始化状态**——一个内存中的对象/结构体。启动时渲染第一帧。
2. **一次读取一个按键（或一行）**，分派给一个改变状态的处理函数。
3. **每次操作后重绘**整帧——不要追加，要替换。
4. **循环直到退出。**

整帧应能放进一屏。

### 5. 让它一条命令就能跑

在项目已有的任务运行器里加一个脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户应当运行 `pnpm run <prototype-name>` 或等价命令——永远不必记住某个路径。

如果宿主项目没有任务运行器，就把命令放在原型 README 的顶部。

### 6. 交接

把运行命令给用户。他们会自己驱动它；有意思的时刻是当他们说"等等，这不应该可能"或者"咦，我以为 X 会不一样"——那些就是**想法本身**里的 bug，而这正是整件事的意义所在。如果他们想加新动作，就加上。原型是会演化的。

### 7. 记录答案

当原型完成了它的使命，问题的答案是唯一值得保留的东西。如果用户在场，就问问他们从中学到了什么。如果不在，就在原型旁边留一个 `NOTES.md`，以便填上答案（如果你看过这次会话，也可以由你来填），然后再删掉原型。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要接到真实数据库。** 用内存存储，除非问题专门关乎持久化。
- **不要泛化。** 不要"万一以后想支持 X 呢"。原型只回答一个问题。
- **不要把逻辑和 TUI 糊在一起。** 如果 reducer / 状态机引用了 `console.log`、提示符或终端转义码，它就不再可移植。把 TUI 保持为纯模块之上的一层薄壳。
- **不要把 TUI 外壳带进生产。** 这层外壳是为在终端里手动驱动而优化的。它背后的逻辑模块才是值得保留的部分。

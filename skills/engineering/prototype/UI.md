# UI Prototype

在单个路由上生成**若干截然不同的 UI 变体**，通过一个浮动底栏来切换。用户在浏览器里切换各变体，选中一个（或从每个里各取一点），然后把其余的丢掉。

如果问题关乎逻辑/状态而非外观——分支选错了。用 [LOGIC.md](LOGIC.md)。

## 什么时候这是对的形态

- "这个页面应该长什么样？"
- "在敲定之前，我想看看这个仪表盘的几个选项。"
- "给设置界面试一个不同的布局。"
- 任何用户否则就会花一整天在脑子里三个模糊草图之间纠结挑选的时候。

## 两种子形态——强烈优先子形态 A

当一个 UI 原型**紧贴着应用的其余部分**时，它要好判断得多——真实的页头、真实的侧栏、真实的数据、真实的密度。一个孤立的用完即弃路由是一个真空：每个变体单独看都还行。只要存在一个合理的既有页面可以承载这些变体，就默认用子形态 A。只有当原型确实没有附近的落脚处时才动用子形态 B。

### 子形态 A —— 对既有页面的调整（首选）

路由已经存在。变体**在同一路由上**渲染，由一个 `?variant=` URL 查询参数把关。既有的数据获取、参数和鉴权都保留——只有渲染部分被替换。这是默认；除非有具体理由，否则就选它。

如果原型针对的东西还没有页面、但*天然会落在某个页面里*（仪表盘的一个新区块、设置界面的一张新卡片、既有流程里的一个新步骤）——那仍然是子形态 A。把变体挂在宿主页面里面。

### 子形态 B —— 一个新页面（最后手段）

只有当被做原型的东西确实没有既有页面可以落脚时才用它——例如一个全新的顶层界面，或一个无法合理嵌入任何地方的流程。

遵循项目已在用的任何路由约定创建一个**用完即弃的路由**——不要发明新的顶层结构。给它起个明显是原型的名字（例如在路径或文件名中包含 `prototype` 一词）。同样的 `?variant=` 模式。

在决定采用子形态 B 之前，做个理智检查：真的没有既有页面能把它嵌进去吗？一个空路由会掩盖那些有内容的页面才会暴露的设计问题。

在两种子形态中，浮动底栏都是相同的。

## 流程

### 1. 陈述问题并选定 N

默认 **3 个变体**。超过 5 个就不再是截然不同、而开始成为噪声了——上限就设在这。

用一行把计划写下来，放在原型所在位置或文件顶部的注释里：

> "设置页面的三个变体，通过 `?variant=` 切换，在既有的 `/settings` 路由上。"

无论用户是否在场提出异议，这都管用。

### 2. 生成截然不同的变体

起草每个变体。让每个都恪守：

- 页面的用途以及它能访问到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同的布局、不同的信息层级、不同的主要可供性，而不只是不同的颜色。三个稍作微调的卡片网格不是 UI 原型，是壁纸。如果两个草稿出来太相似，就带着明确的"不要用卡片网格"指引重做一个。

### 3. 把它们接起来

在路由上创建一个单一的切换器组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（既有页面）：把所有既有的数据获取保留在切换器之上；每个变体只改变渲染的子树。

对于子形态 B（新页面）：`/prototype/<name>` 下的用完即弃路由挂载同一个切换器。

### 4. 构建浮动切换器

屏幕底部居中的一个小型固定定位栏，含三个部件：

- **左箭头**——切换到上一个变体（循环回绕）。
- **变体标签**——显示当前变体键，如果变体导出了名字，也一并显示。例如 `B — Sidebar layout`。
- **右箭头**——向前切换（循环回绕）。

行为：

- 点击箭头更新 URL 查询参数（使用框架的路由器——Next 上用 `router.replace`，React Router 上用 `navigate` 等），这样变体可分享且刷新后保持稳定。
- 键盘：`←` 和 `→` 方向键也可切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于聚焦状态时，不要拦截方向键。
- 视觉上与页面区分开（例如高对比度胶囊、微妙阴影），使它显然不属于正在被评估的设计。
- 在生产构建中隐藏——以 `process.env.NODE_ENV !== 'production'` 或等价检查把关，这样一次误合的原型也不会把这个栏发给用户。

把切换器放在一个单一的共享组件里，让两种子形态都能复用它。把它放在项目中共享 UI 所在的地方。

### 5. 移交

给出 URL（以及 `?variant=` 各键）。用户会在有空时逐一切换。有意思的反馈通常是**"我想要 B 的页头配 C 的侧栏"**——那才是他们真正想要的设计。

### 6. 沉淀答案并清理

一旦某个变体胜出，先沉淀答案——哪个变体、为什么——然后按 [SKILL](SKILL.md) 所述的方式沉淀原型。把胜者融入真实代码，把其余的挪到用完即弃分支，而不是并进 main：

- **子形态 A**——把胜者融入既有页面；把落选的变体和切换器从 main 中去掉。
- **子形态 B**——把胜出的变体提升为一个真实路由；把用完即弃的路由和切换器从 main 中去掉。

整套变体是一手来源，所以它落在用完即弃分支上，而不是垃圾桶里——留在 main 分支里的变体组件和切换器会很快腐坏，并让下一个读者困惑。

## 反模式

- **只在颜色或文案上有差别的变体。** 那是微调，不是原型。真正的变体在结构上意见相左。
- **在变体之间共享过多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了初衷。每个变体都应能自由抛弃布局。
- **把变体接到真实的 mutation 上。** 只读的原型没问题。如果某个变体需要 mutate，就把它指向一个桩（stub）——问题是"这东西应该长什么样"，不是"后端能不能工作"。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（没有测试、极简的错误处理）。把它融入时要好好重写。

# UI 原型（UI Prototype）

在同一个路由上生成**几个截然不同的 UI 变体**，通过一个悬浮底栏来切换。用户在浏览器里在各变体之间翻看，挑一个（或从每个里偷一些），然后把其余的扔掉。

如果问题关乎逻辑/状态而非外观——选错分支了。用 [LOGIC.md](LOGIC.md)。

## 什么时候这是正确的形态

- "这个页面应该长什么样？"
- "我想在拍板之前先看几个这个仪表盘的方案。"
- "给设置页换个布局试试。"
- 任何用户本来要花一天时间在脑中三个模糊草图之间纠结的场合。

## 两个子形态——强烈偏向子形态 A

UI 原型在**贴着应用其余部分**时——真实的页头、真实的侧边栏、真实的数据、真实的密度——要好判断得多。一个孤立的一次性路由就是个真空：每个变体在孤立状态下看起来都还行。只要存在一个合理的现有页面可以承载这些变体，就默认选子形态 A。只有当原型确实无处安放时才动用子形态 B。

### 子形态 A——对现有页面的调整（首选）

路由已经存在。变体**渲染在同一个路由上**，由 `?variant=` URL 查询参数控制。现有的数据获取、参数和鉴权全部保留——只有渲染部分切换。这是默认选项；除非有特定理由，否则选它。

如果原型针对的东西还没有页面、但**自然会存在于某个页面之内**（仪表盘的新区块、设置页的新卡片、现有流程的新步骤）——那仍然是子形态 A。把变体挂载进宿主页面。

### 子形态 B——一个新页面（最后手段）

只有当要做原型的东西确实没有现成页面可以容身时才用它——比如一个全新的顶层界面，或者一个无法被嵌入任何合理位置的流程。

按项目已有的路由约定创建一个**一次性路由**——不要发明新的顶层结构。给它起个一看就是原型的名字（例如在路径或文件名里包含 `prototype` 一词）。使用同样的 `?variant=` 模式。

在拍板用子形态 B 之前，先核实一下：真的没有现成页面能把它嵌进去吗？空路由会掩盖那些有内容的页面才会暴露出来的设计问题。

在两个子形态里，悬浮底栏都是相同的。

## 流程

### 1. 陈述问题并确定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音——以此为上限。

把计划用一行写下来，写在原型所在的位置或文件顶部注释里：

> "设置页的三个变体，通过 `?variant=` 切换，挂在现有的 `/settings` 路由上。"

无论用户是来提反对意见还是不在场，这都适用。

### 2. 生成截然不同的变体

起草每个变体。每个都要满足：

- 页面的用途以及它能访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**——不同的布局、不同的信息层级、不同的主要操作方式，而不只是不同的颜色。三个略微调过的卡片网格不是 UI 原型，那是墙纸。如果两个草稿出来太像了，就用明确的"不要用卡片网格"的指引重做一个。

### 3. 把它们接起来

在路由上创建一个单独的切换组件：

```tsx
// 伪代码——按项目的框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对子形态 A（现有页面）：把所有现有的数据获取保留在切换器之上；每个变体只改变被渲染的子树。

对子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中的一个固定定位小栏，包含三个部分：

- **左箭头**——切到上一个变体（循环回绕）。
- **变体标签**——显示当前变体的键，如果变体导出了名字，也显示那个名字。例如 `B — Sidebar layout`。
- **右箭头**——往前切（循环回绕）。

行为：

- 点击箭头更新 URL 查询参数（用框架的路由器——Next 上用 `router.replace`，React Router 上用 `navigate` 等），让变体可分享、刷新后稳定。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于聚焦状态时，不要拦截方向键。
- 在视觉上与页面区分开（例如高对比度的胶囊、淡淡的阴影），让它明显不属于正在被评估的设计。
- 在生产构建里隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查来设门槛，这样误合并的原型也无法把这个栏带给用户。

把切换器放进一个共享组件里，让两个子形态都能复用。把它放在项目里存放共享 UI 的地方。

### 5. 交接

把 URL（以及 `?variant=` 的键）告诉用户。他们有空时会逐个翻看。最有价值的反馈通常是**"我想要 B 的页头配 C 的侧边栏"**——那才是他们真正想要的设计。

### 6. 记录答案并清理

一旦某个变体胜出，就写下是哪个、为什么（提交信息、ADR、issue，或者如果离线运行且用户尚未回复时，写在紧挨着原型的 `NOTES.md` 里）。然后：

- **子形态 A**——删掉落选的变体和切换器；把胜者折叠进现有页面。
- **子形态 B**——把胜出变体提升为正式路由，删掉一次性路由和切换器。

不要把变体组件或切换器丢在那里。它们腐烂得很快，会把下一位读者搞糊涂。

## 反模式

- **只在颜色或文案上有差别的变体。** 那是微调，不是原型。真正的变体在结构上各执己见。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了初衷。每个变体都应能自由地把布局推翻重来。
- **把变体接到真实的写操作上。** 只读原型没问题。如果某个变体需要写，就让它指向一个桩——问题是"这东西应该长什么样"，而不是"后端能不能用"。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（没测试、最少的错误处理）。折叠进去时要重新好好写一遍。

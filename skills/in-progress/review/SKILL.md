# 评审（Review）

对 `HEAD` 与用户提供的某个固定点之间的差异（diff）进行双维度评审：

- **标准（Standards）** —— 代码是否符合本仓库已记录的编码标准？
- **规格（Spec）** —— 代码是否忠实地实现了最初的 issue / PRD / 规格？

两个维度都作为**并行子代理**运行，从而避免彼此污染各自的上下文，然后由本技能汇总它们的发现。

issue 跟踪器的信息应已提供给你 —— 如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户所说的就是固定点 —— 一个 commit SHA、分支名、标签、`main`、`HEAD~5` 等等。不要带主观倾向，原样传递即可。如果他们没有指定，就询问："对照什么进行评审 —— 一个分支、一个 commit，还是 `main`？" 在拿到答案之前不要继续。

一次性确定 diff 命令：`git diff <fixed-point>...HEAD`（三点形式，使比较针对合并基准 merge-base 进行）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

### 2. 确定规格来源

按以下顺序查找最初的规格：

1. commit 信息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）—— 通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD/规格文件。
4. 如果什么都没找到，询问用户规格在哪里。如果他们说没有规格，则**规格（Spec）**子代理将跳过并报告"无可用规格"。

### 3. 确定标准来源

仓库中任何记录了代码应如何编写的内容。常见位置：

- `CLAUDE.md`、`AGENTS.md`
- `CONTRIBUTING.md`
- `CONTEXT.md`、`CONTEXT-MAP.md`、各上下文的 `CONTEXT.md` 文件
- `docs/adr/`（架构决策也是标准）
- `.editorconfig`、`eslint.config.*`、`biome.json`、`prettier.config.*`、`tsconfig.json`（机器强制执行的标准 —— 记录它们，但不要重复检查工具已经检查过的内容）
- 仓库根目录或 `docs/` 下的任何 `STYLE.md`、`STANDARDS.md`、`STYLEGUIDE.md` 或类似文件

收集这些文件的列表。**标准（Standards）**子代理将读取它们。

### 4. 并行启动两个子代理

在单条消息中发送两个 `Agent` 工具调用。两者都使用 `general-purpose` 子代理。

**标准子代理提示词** —— 应包含：

- 完整的 diff 命令和 commit 列表。
- 你在第 3 步找到的标准来源文件列表。
- 简报："阅读标准文档。然后阅读 diff。逐文件/逐 hunk（在相关处）报告 diff 违反已记录标准的每一处。引用该标准（文件 + 规则）。区分硬性违规与判断性问题。跳过任何工具已强制执行的内容。控制在 400 字以内。"

**规格子代理提示词** —— 应包含：

- diff 命令和 commit 列表。
- 规格的路径或已获取的内容。
- 简报："阅读规格。然后阅读 diff。报告：(a) 规格要求但缺失或仅部分实现的需求；(b) diff 中并未被要求的行为（范围蔓延）；(c) 看似已实现但实现方式看起来有误的需求。每条发现都引用规格中的对应行。控制在 400 字以内。"

如果规格缺失，则跳过规格子代理并在最终报告中说明这一点。

### 5. 汇总

将两份报告分别放在 `## Standards` 和 `## Spec` 标题下呈现，逐字保留或仅做轻微整理。**不要**合并或重新排序发现 —— 这两个维度被刻意分开，以便用户能够独立地看到它们。

最后给出一行总结：每个维度的发现总数，以及（如有）被标记出的最严重的单个问题。

## 为什么要分两个维度

一个改动可能通过一个维度却在另一个维度上失败：

- 遵循了所有标准但实现了错误的东西的代码 → **标准通过，规格失败。**
- 完全照 issue 要求去做但破坏了项目约定的代码 → **规格通过，标准失败。**

分开报告可以防止一个维度掩盖另一个维度。

# 问题追踪器集成仅限主流工具

`setup-matt-pocock-skills` 只为**主流**问题追踪器提供一等支持。要求添加对小众、新兴或单一厂商的实验性追踪器的支持，属于范围之外。

## 为什么这超出范围

每个问题追踪器后端都会把一套 CLI 形态硬编码进技能中（命令、参数、输出解析）。每新增一个后端都是永久性的维护负担——它必须随着工具 CLI 的演进持续可用，并且必须持续针对 `/to-prd`、`/to-issues`、`/triage` 等技能进行测试。只有当某个追踪器被相当一部分用户真正使用时，这个成本才值得付出。

"主流"是一种判断，而非数字门槛：

- GitHub、GitLab 和 Backlog.md 属于我们会视为主流的那类工具——广为人知、被广泛使用、早已过了实验阶段。
- 一个全新的、面向 agent 的工具，哪怕设计再有趣，只有几百个 GitHub star，也不算主流。

Star 数、年限和下载量在做判断时是有用的信号，但没有一个是规则本身。规则是：一个典型的工程师会认得这个工具，并且有可能为团队选择它吗？

针对非主流追踪器的应急方案已经存在：

- `local markdown`，用于轻量级的仓库内追踪。
- `other/custom`，供想自己接入某些东西的用户使用。

两者都不需要核心技能了解具体的工具。

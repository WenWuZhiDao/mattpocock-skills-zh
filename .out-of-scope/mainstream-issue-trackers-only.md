# 问题跟踪器集成仅限于主流工具

`setup-matt-pocock-skills` 只对**主流**问题跟踪器提供一等支持。要求添加对小众、新兴或单一厂商实验性跟踪器的支持，属于范围之外。

## 为什么这属于范围之外

每一种问题跟踪器后端都会把一套 CLI 形态硬编码进技能里（命令、参数、输出解析）。每个新后端都是永久的维护面——它必须随着工具 CLI 的演进持续可用，还必须持续针对 `/to-spec`、`/to-tickets`、`/triage` 及其伙伴接受测试。只有当某个跟踪器被相当一部分用户实际使用时，这份成本才值得付出。

"主流"是一个判断，而非一条数值门槛：

- GitHub、GitLab 和 Backlog.md 是我们会视为主流的那类工具——广为人知、广泛使用、早已过了实验阶段。
- 一个全新的、面向代理的、只有几百个 GitHub star 的工具则不是，无论其设计多么有趣。

Star 数、诞生时间和下载量在做判断时是有用的信号，但它们中没有一个是规则本身。规则是：一个典型的工程师会认得这个工具，并有可能为他的团队选择它吗？

针对非主流跟踪器的变通途径已经存在：

- `local markdown`，用于轻量的仓库内跟踪。
- `other/custom`，供想要自行搭建的用户使用。

两者都不要求核心技能了解具体的工具。

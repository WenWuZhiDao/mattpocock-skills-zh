# 撰写文档页

`engineering/` 和 `productivity/` 中的每个技能，都有一个面向人的**文档页**，位于 `docs/<bucket>/<skill-name>.md`——文档树镜像了 `skills/` 下这两个分桶文件夹。它发布在 `https://aihero.dev/skills-<skill-name>`；无论属于哪个分桶，URL 始终是 `skills-<skill-name>`，因此文档路径只是仓库的组织方式而已。页面不是技能，也不是 `SKILL.md` 的副本。只有这两个分桶会被提升；其余的（`misc/`、`in-progress/`、`deprecated/`）不发布任何文档页。

这些技能大多是**用户调用型**的：智能体永远不会替你触发它们，所以*你*就是那个必须记住它们存在、以及何时该用它们的索引。那份记忆是**认知负荷**。文档页的职责就是缓解它——让一个读者围绕一个技能建立方向感，从而能把它装进脑子里，知道何时该用它，并看清它在系统中的位置。这些页面合在一起是一个分布式路由器；每一页都是一个节点。

每当一个已提升的技能被新增、重命名或行为发生变化时，都要行动：创建或重新同步它的文档页。重命名也会移动文件（`docs/<bucket>/<old>.md` → `docs/<bucket>/<new>.md`），因为已发布的 URL 跟随名字；在 `engineering/` 和 `productivity/` 之间移动的技能，会把它的文档文件移动到对应的文件夹。`misc/`、`in-progress/` 和 `deprecated/` 中的技能不获得页面——这些分桶都没有被提升。一个从其中之一移动*出去*、进入 `engineering/` 或 `productivity/` 的技能会获得页面；反向移动的则失去它。

因为这些页面发布在 `aihero.dev` 上，**每个链接都是绝对链接**——绝不用仓库相对路径。指向另一个技能的链接指向 `https://aihero.dev/skills-<name>`；指向仓库内的链接指向它完整的 `https://github.com/mattpocock/skills/...` URL。一个在仓库里能用的相对链接，一旦发布就会失效。

没有 H1——已发布的页面从 slug 取它的标题。

## 页面结构

填写下方模板，保持其顺序。**固定框架**（`## 它做什么`、`## 何时使用它`、`## 它的位置`）出现在每一页上。`## 前置条件` 和自由形式的实质小节只承载这个特定技能所需的内容；其余的删掉。

有四个小节能让一页值得一读：`它做什么`、`何时使用它`、`常见问题`、`它生效的标志`。前两个为读者建立方向感；后两个是页面从概述技能转为回答读者自身处境的地方。后两个各有一条要达到的标准，见下文——但把一页既没达到其一也没达到其二的情况当作未完成，而不是完成而简短。

**一页不承载任何安装命令。** ai-hero 页面模板会自行渲染安装小组件——一个复制按钮、单技能命令、整套命令，以及更新那一行——放在正文上方。一个也把它们写出来的页面，会给读者展示同一条命令两次，而这两份副本会漂移：每页上手写的那一对相对于旁边的小组件已经过时。安装措辞是站点的属性，而非页面的属性。如果需要改动，就在 ai-hero 里改；标准措辞见[安装文案块](./install-block.md)。

## 它做什么

一到两段平实的语言。开头给出技能一句话的职责，然后陈述**决定性约束**——那个让这个技能行为不同于显而易见的默认做法的唯一事实（对 `to-spec` 而言：它不会再次访谈用户，而是综合已知的信息）。把它写成一个平实的陈述句——绝不要写成「决定性约束：」或「关键在于：」这样的带标签旁白；那种套路读起来像填充物。这一行是页面上最有价值的一行；绝不省略它。

## 何时使用它

你如何、何时用到这个技能——两个要点，两者实际上总是同时存在：

- **调用方式。** 说明是你输入它，还是智能体触发它。一个用户调用型技能：「你通过输入 `/<name>` 来调用它——智能体不会自行去用它。」一个模型调用型技能：「输入 `/<name>`，或者当任务契合时智能体会自动去用它。」
- **触发边界。** 索引条目：「在……时使用它」。当这个技能容易与某个同类混淆时，补上另一半——「若是要做 <X>，改用 [<sibling>](https://aihero.dev/skills-<sibling>)。」

## 前置条件

可选——只在技能需要某样东西就位才能运作时才包含；否则整个标题都省略。它涵盖：一个**它写入的工作区**（像 `grill-with-docs` 这样的有状态技能会写 `CONTEXT.md` 和 ADR；`teach` 会搭建一整个目录——说明它写什么、写到哪里）、**前置设置**（`triage`/`to-spec`/`to-tickets` 需要 `setup-matt-pocock-skills` 已配置好一个 issue 追踪器），或**仓库特定的工具**。一个能在任何地方运行的无状态技能没有前置条件——删掉这一小节。

## <自由形式的中段>

一到三个简短小节，用技能*自己的词汇*，让它豁然开朗——选择任何契合这个技能的标题：它跑的循环、它产出的工件、它做出的分岔、它消灭的那个反模式。没有规定的标题；这些技能太异质，无法统一。

唯一不可让步的一点：**凸显技能的领头词／决定性理念**——`tight` 反馈回路、`deep module`、用一次性代码回答问题、red-green。它有双重回报：读者既学到这个技能*是什么*，也学到那个日后会用来*想起去用它*的词。

## 常见问题

读者真正会问的关于这个技能的问题，每个用粗体列出，答案写在其下方的几行里——不用子标题。

一个真实观察到的问题总胜过一个臆造的，所以在动笔前先去找它们：

- **wiki。** 如果这台机器上存在 `~/repos/matt/personal-wiki`，它就是最丰富的来源。它的 `wiki/audience/` 区域围绕受众想要什么、讨论什么、以及**被什么搞糊涂**来组织——先读 `wiki/index.md` 获取页面清单，再读与这个技能相关的页面。每个页面都带有 `sources:` 反向链接，指向原始的 X、Discord、GitHub 和邮件线程；wiki 是二手来源，所以引用提问者本人的问题，而非 wiki 对它的概括。目录不存在时跳过这一条。
- **本仓库的 issues。** `gh issue list --repo mattpocock/skills --search "<skill-name>" --state all`。一个被提交了两次的问题，就是页面欠着一个答案的问题。
- **`CHANGELOG.md`。** 任何被重命名、移动或行为变更的东西都会产生一个「它去哪了？」的问题，而页面必须回答它。

当搜寻结果稀薄时，本小节也可以承载一个读者显然会问的问题——但**数量要对证据诚实**。一个被充分讨论的技能配得上六个；一个冷门的配得上一两个，或一个都没有。把一个稀薄的技能硬撑到与丰富技能一样，正是本小节塞满无人会问的问题的方式，而一个臆造的问题教不了读者任何东西。

按每个问题出现的频率排序，最尖锐的在前，并在真实之处说出那句不中听的话——一次很长的 grilling 会话通常意味着范围太大了；一个被要求写自己技能的模型会产出冗长的东西。没有什么值得回答时，省略这个标题。

## 它生效的标志

几个要点，说出读者在技能正常运作时会看到什么。每一条的标准是：读者无需打开 `SKILL.md` 就能核对——是他们自己工作中的一个信号，或是眼前的运行痕迹里的一个信号。「文档越好就越短」通过了；「library 小节与 `template.sh` 逐字节相同」是对技能内部的一次合规检查，只是套了本小节的名字。在这些迹象清晰的地方都包含它；在它们仍然模糊的地方省略这个标题。

## 它的位置

总是出现。用一两句话把技能安置在系统中：

- **角色。** 点明它：一个**链条中的一步**（`grill-with-docs → to-spec → to-tickets → implement → code-review`）、一个**只跑一次的设置**（`setup-matt-pocock-skills`）、**周期性维护**（`improve-codebase-architecture`，「每隔几天」），或一个**随时可用的独立技能**（`diagnosing-bugs`、`prototype`、`handoff`）。一个独立技能的定位就是一句诚实的话——远胜于省略这一小节。
- **邻居。** 那一两个要紧的同类，每个都带一个 because 从句，用绝对链接。
- **地图。** 指向 [ask-matt](https://aihero.dev/skills-ask-matt)——覆盖整套的路由器——这样本页就保持是一个节点，永远不必重绘整张图。

## 约定

- 解释**为什么**，而非过程。页面为技能建立方向感、把它安置好；它绝不复述 `SKILL.md` 的步骤或模板堆砌——一个正在选工具的人不需要那份操作手册。
- **绝不点名作者。** 页面是一份技术文档，不是谁说了什么的记录。「Matt 说」「Matt 自己的答案」「他的立场是」、一段被引用的回复——全都去掉。搜寻问题得到的一个发现值得保留；它的出处不值得。把实质陈述成对技能的一个平实断言（「修复办法是一条直接指令：……」「这个划分归根结底在于会话数量」），并抛掉那个框架。读者是在决定要不要用一个工具；一个观点无论如何分量相同，而一个带出处的观点会在立场变动的那一刻就过时。引用一个*用户*仍然没问题——「一位用户报告……」是关于这个技能在真实世界中的证据，且保持匿名。
- 使用技能的**领头词**（_seam_、_deep module_、_tracer bullet_），让页面和技能说同一种语言。
- **在有对应词条时使用 [AI 编码词典](https://www.aihero.dev/ai-coding-dictionary)的术语，并在页面上首次使用处加链接。** 该词典是 AI 编码的通用词汇——_context window_、_subagent_、_harness_、_primary source_、_agent mode_。优先用它的词，而非你自造的同义词。把每个术语在页面上的首次出现链接到 `https://www.aihero.dev/ai-coding-dictionary/<slug>`（slug 是术语的小写、非字母数字替换为连字符：_context window_ → `context-window`），之后每次出现都不加链接。只在词语确实承载词典含义时才加链接——一个领域*模型*、背景*上下文*或一个鉴权*令牌*是恰好字面相同的另一个词。绝不在标题、代码片段或已有链接内加链接，也绝不给一个指代本仓库某个技能而非该概念的词加链接。完整术语表，若这台机器上存在 `~/repos/ai/ai-coding-dictionary/dictionary/` 就读它——每个术语一个文件，文件名*就是*术语——否则读 [mattpocock/dictionary-of-ai-coding](https://github.com/mattpocock/dictionary-of-ai-coding)，无论哪种它都是事实来源。
- **分支要放进表格或列表，绝不放进段落。** 当页面呈现一个选择时——技能能产出的两种工件、触发它的四种处境、某个边界上的五个选项——读者是在扫读，找那一行匹配自己处境的。段落逼他们读完全部才能弄清。一个简短的 markdown 表格（左列是条件，右列是该做什么）或一个带项目符号的列表，能让它一眼看清。凡有分支出现的地方都适用，最常见于 `## 何时使用它` 和自由形式的中段。
- 让页面本身保持低负荷。它是一份*关于*低认知负荷技能的文档；家具（多余的标题、重述的链接）正是它所反对的东西。

## 完成判据

- 页面存在于 `docs/<bucket>/<name>.md`，且重命名或分桶移动后没有过时页面残留。
- 页面不承载任何来源链接，也不自行写任何安装命令。
- `## 它做什么` 陈述了决定性约束，作为平实散文而非带标签的旁白。
- 页面不点名作者、不引用作者——每个断言都自立。
- `## 何时使用它` 陈述了调用方式和触发边界。
- `## 它的位置` 点明了角色并链接到 `ask-matt`。
- 在存在前置条件（工作区、前置设置、工具）的地方陈述了它，在不存在的地方这一小节缺席。
- 中段凸显了领头词。
- 页面用到的每个 AI 编码词典术语都按词典的写法拼写，且它的首次使用——且仅首次使用——链接到词典条目。
- 每个多路分支都是表格或列表，而非读者必须读完的段落。
- 对真实问题的搜寻确实进行过——wiki、issues、changelog——且 `## 常见问题` 的规模贴合它所找到的，而非撑到与某个更丰富技能的页面相当。
- 每个 `## 它生效的标志` 要点都无需打开 `SKILL.md` 即可核对。
- 各小节按模板的顺序出现。
- 每个链接都是绝对链接，且每个都能解析。

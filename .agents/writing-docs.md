# 撰写文档页

`engineering/` 和 `productivity/` 中的每个技能都有一个面向人的**文档页**，位于 `docs/<bucket>/<skill-name>.md`——文档树镜像了 `skills/` 下的这两个分桶文件夹。它发布在 `https://aihero.dev/skills-<skill-name>`；无论属于哪个桶，URL 始终是 `skills-<skill-name>`，因此文档路径纯粹是仓库组织方式。这个页面不是技能本身，也不是 `SKILL.md` 的副本。只有这两个桶会被推广；其余的（`misc/`、`personal/`、`in-progress/`、`deprecated/`）不发布文档页。

这些技能大多是**用户调用型**：代理永远不会替你触发它们，所以*你*就是那个必须记住它们存在、以及何时该伸手去用的索引。那份记忆就是**认知负荷**。文档页的职责就是减轻它——让一个读者围绕一个技能定位方向，从而能把它装进脑子里，知道何时该用它，并看清它在整个体系中的位置。这些页面合起来是一个分布式路由器；每一页都是一个节点。

每当一个已推广技能被添加、重命名或改变行为时都要行动：创建或重新同步它的文档页。重命名也会移动文件（`docs/<bucket>/<old>.md` → `docs/<bucket>/<new>.md`），因为发布的 URL 跟随名称；在 `engineering/` 与 `productivity/` 之间迁移的技能，会把它的文档文件移动到对应的文件夹。`misc/`、`personal/`、`in-progress/` 和 `deprecated/` 中的技能不获得页面——这些桶都不被推广。一个技能*移出*其中之一进入 `engineering/` 或 `productivity/` 时会获得页面；反向移动的则会失去页面。

因为这些页面发布在 `aihero.dev` 上，**每个链接都是绝对链接**——绝不能用相对于仓库的路径。指向另一个技能的链接指向 `https://aihero.dev/skills-<name>`；指向仓库内部的链接则指向其完整的 `https://github.com/mattpocock/skills/...` URL。在仓库里能用的相对链接，一旦发布就会失效。

没有 H1——发布出来的页面从 slug 取标题。

## 它做什么

一到两段平实的文字。开头点明技能一句话的职责，然后陈述其**决定性约束**——那个让这个技能与显而易见的默认做法表现不同的唯一事实（对 `to-spec` 而言：它不会再次访谈用户，而是综合已经掌握的信息）。把它写成一句平实的陈述句——绝不要写成带标签的旁注，如"决定性约束："或"关键之处："；那种公式化写法读起来像填充物。这一行是整页最有价值的内容；绝不要省略。

## 何时使用它

你如何以及何时伸手去用这个技能——两个要点，两者几乎总是同时出现：

- **调用方式。** 说明是你输入它，还是代理触发它。用户调用型技能："你通过输入 `/<name>` 来调用——代理不会自行伸手去用它。"模型调用型技能："输入 `/<name>`，或者当任务合适时代理会自动伸手去用它。"
- **触发边界。** 索引条目："在……时伸手去用它"。当这个技能与某个同类技能容易混淆时，补上另一半——"要做 <X>，改用 [<sibling>](https://aihero.dev/skills-<sibling>)。"

## 前置条件

可选——仅当技能需要某样东西就位才能运作时才包含；否则整节省略。涵盖：它**写入的工作区**（像 `grill-with-docs` 这样的有状态技能会写入 `CONTEXT.md` 和 ADR；`teach` 会构建一整个目录——说明它写什么、写到哪里）、**前置设置**（`triage`／`to-spec`／`to-tickets` 需要 `setup-matt-pocock-skills` 已配置好问题跟踪器），或**仓库特定的工具**。一个能在任何地方运行的无状态技能没有前置条件——去掉这一节。

## <自由形式的中段>

一到三个简短章节，用技能*自己的词汇*，让它豁然开朗——挑选任何契合该技能的标题：它运行的循环、它产出的制品、它做出的分岔、它消灭的那个反模式。没有规定的标题；这些技能太异质，无法用一个统一的标题。

唯一不可妥协的一点：**凸显技能的领头词／决定性理念**——`tight` 反馈循环、`deep module`（深模块）、用一次性代码回答一个问题、红-绿。它有双重回报：读者既学到技能*是*什么，又学到那个日后用来*伸手去用*它的词。

## 它生效的标志

可选。一份简短、可核对的清单，列出那些告诉读者技能确实在履行职责的可观察信号——它触发时读者应该看到什么，以及借由这些信号的缺席看出它没有触发。当一个技能有清晰的迹象时才包含它（例如 `to-spec` 不再访谈你就写出内容；某个领头词在轨迹中反复出现）；当信号模糊时省略这个标题。几个要点即可，不要更多。

## 它的位置

始终出现。用一两句话把技能放到体系中定位：

- **角色。** 给它命名：一个**链条环节**（`grill-with-docs → to-spec → to-tickets → implement → code-review`）、一次**一次性设置**（`setup-matt-pocock-skills`）、**周期性维护**（`improve-codebase-architecture`，"每隔几天"），或一个**随时可伸手去用的独立技能**（`diagnosing-bugs`、`prototype`、`handoff`）。独立技能的地图就是一句诚实的话——远胜于省略这一节。
- **邻居。** 那一两个要紧的同类技能，各带一个 because 从句，用绝对链接链接。
- **地图。** 指向 [ask-matt](https://aihero.dev/skills-ask-matt)，即覆盖整套技能的路由器，好让这一页保持为一个节点，永远无需重绘整张图。

## 约定

- 解释**为什么**，而不是过程。页面为技能定位和安放；它绝不复述 `SKILL.md` 的步骤或模板堆砌——一个正在选工具的人不需要操作手册。
- 使用技能的**领头词**（_seam_（接缝）、_deep module_（深模块）、_tracer bullet_（曳光弹）），让页面与技能说同一种语言。
- 让页面自身保持低负荷。它是*关于*低认知负荷技能的文档；累赘的东西（多余的标题、重复的链接）正是它所反对的。

## 完成判据

- 页面存在于 `docs/<bucket>/<name>.md`，且重命名或换桶后没有陈旧页面残留。
- Quickstart 块和源码链接指明了正确的桶和技能；update 那一行指明了技能名。
- `## 它做什么` 以平实散文而非带标签的旁注陈述了决定性约束。
- `## 何时使用它` 陈述了调用方式和触发边界。
- `## 它的位置` 指明了角色并链接到 `ask-matt`。
- 存在前置条件（工作区、前置设置、工具）之处已陈述前置条件，不存在之处则没有这一节。
- 中段凸显了领头词。
- 每个链接都是绝对链接，且每个都能解析。
